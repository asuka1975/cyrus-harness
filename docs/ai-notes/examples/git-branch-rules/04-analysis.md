# 情報の分析

## 素材の要点
- 依頼文（口頭）: 先月、新人が main に直接 push する事故が2回あった。これが文書のきっかけ。
- 事故の影響（ユーザーの証言）: 1回目はビルドが壊れ、半日チーム全員の作業が止まった。2回目は未レビューの変更が本番に出かけ、リリース直前に気づいて戻した。
- 社内ルール（ユーザーの証言）: GitHub を使う。ブランチ名は feature/<内容> か fix/<内容>。プルリクエストには1名以上の承認が必要。マージは squash merge で、プルリクエストを出した本人が行う。
- 仕組みの予定: main への直接 push を拒否する設定に来月変える。今はまだ push できてしまう。

## 読者に必要な情報

### なぜ main に直接 push してはいけないのか
- main はチーム全員が共有する土台で、本番に出るもとになる。
- 実際の事故2件の影響（半日の作業停止・本番に出かけた未レビューの変更）。
- 今はまだ仕組みで止められないので、自分で守る必要がある。

### ブランチとは何で、なぜ作業ごとに切るのか
- ブランチは、main から枝分かれした自分専用の作業場所。そこでの commit は main に影響しない。
- 作業ごとに分けると、レビューとマージを作業単位で行える。

### 作業ブランチはどうやって切ればよいのか
- 最新の main を取り込んでから `git switch -c feature/<内容>` で作る。
- 名前は feature/<内容>（新しい機能）か fix/<内容>（不具合の修正）。

### プルリクエストとは何で、どうやって出すのか
- 「このブランチの変更を main に取り込んでください」という依頼。GitHub 上で作る。
- ブランチを push したあと、GitHub の画面から作成し、レビューする人を指定する。

### レビューでは何を見られ、指摘されたらどうすればよいのか
- ほかの人が変更を読み、問題がないかを確かめる。1名以上の承認が必要。
- 指摘は同じブランチに commit して push すれば、プルリクエストに反映される。

### マージは誰が、いつ行うのか
- 承認を受けたあと、プルリクエストを出した本人が squash merge で行う。
- squash merge は、ブランチの commit を1つにまとめて main に取り込む方法。

## 載せない情報
- rebase やコンフリクト解消の詳しい手順: 新人が最初の1本を通すには不要で、10分の分量を超える。別の資料に任せる。
- Git の内部の仕組み（コミットのグラフなど）: 運用ルールを守るのに不要。
- merge commit / rebase merge との比較: 社内は squash merge に決まっており、選ぶ場面がない。
- ブランチ保護の設定方法: 設定するのは管理者で、読者の作業ではない。
- 事故を起こした人の特定につながる情報: 目的に不要で、責める文書にしないため。

## 不足している情報
- 社内ルールと事故の影響は、ユーザーの証言のみ（user_asserted として扱う）。
- GitHub の仕様（ブランチ保護で直接 push を拒否できること、squash merge の動き、承認数の必須設定、同じブランチへの push がプルリクエストに反映されること）: ステージ6で公式ドキュメントを調べる。〔調査〕
- `git switch -c` でブランチを作れること: ステージ6で実行して確かめる。〔実行〕

## 論点
- 「来月から仕組みで止められるなら、覚えなくてよいのでは」: 仕組みは push を拒否するだけで、正しい流れは教えない。今月はまだ止まらない。
- 「小さな修正なら直接 push してもよいのでは」: 変更の大小を問わず、例外は作らない（社内ルール）。事故の変更の規模は不明なので、本文では規模に触れない。
- 「レビューを待つと遅くなるのでは」: 待ち時間と戻す手間を比べる数字はない。本文では比較せず、事故の影響を示すにとどめる。
- 「承認後に誰がマージするのか分からない」: 出した本人が行う、と明記する。
- 「承認後に commit を足したらどうなるか」: その commit も同じプルリクエストに入る。承認が自動で取り消されるかは設定しだいで不明なので、もう一度見てもらうよう勧める。
