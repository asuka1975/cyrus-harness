# 背景と素材

## 提供された素材

## 聞き取りメモ
- 〔事実〕先月、新人が main に直接 push してしまう事故が2回あった。これが文書を作るきっかけ。
- 〔事実〕読者は今年入社の新人エンジニア。Git の commit と push はできるが、ブランチ運用は知らない。
- 〔事実〕読者はオンボーディング中に、10分ほどかけてじっくり読む。
- 〔事実〕掲載先は社内Wiki。形式は Markdown の解説で、3000字程度。
- 〔意見〕読後に、作業ブランチを切り、プルリクエストを出し、レビューを受けてからマージできるようになってほしい。
- 〔意見〕「PR」という略語は使わず、「プルリクエスト」と書く。

- 〔事実〕社内では GitHub を使っている。
- 〔事実〕main のブランチ保護で直接 push を拒否する設定に、来月変える予定。今はまだ拒否されない。
- 〔事実〕作業ブランチの名前は feature/<内容> または fix/<内容>。
- 〔事実〕プルリクエストには1名以上の承認が必要。
- 〔事実〕マージは squash merge で、プルリクエストを出した本人が行う。
- 〔事実〕1回目の事故ではビルドが壊れ、半日チーム全員の作業が止まった。
- 〔事実〕2回目の事故では未レビューの変更が本番に出かけ、リリース直前に気づいて戻した。
