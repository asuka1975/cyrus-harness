# cyrus ハーネスの設計と使い方

この文書は AI が書いたメモです。`docs/workflow.md` のワークフローを、どう実装したかを説明します。

## 使い方

1. Claude Code をこのリポジトリで起動する。
2. `/cyrus 書きたい文書のテーマ` と入力する。進行中の文書があれば、`/cyrus` だけで続きから再開する。
3. Claude の質問に答えていく。途中で「目的」「読者」「主張」「話の流れ」「完成版」の5か所で承認を求められる。
4. 完成版は `documents/<slug>/final.md` にできる。

進捗は `/cyrus-status` で確かめられます。

ハーネスを変更したら、`apm install` で `.claude/` に展開し直します。テストは `python3 -m unittest discover -s tests` で実行します。

## 全体の構成

ハーネスは APM パッケージとして作っています。部品は `.apm/` に置き、`apm install` で `.claude/` に展開します。

| 部品 | 置き場所（.apm/） | 役割 |
| --- | --- | --- |
| スキル | `skills/cyrus/SKILL.md` | 全体の進め方とインタビューの作法 |
| ステージのガイド | `skills/cyrus/stages/01〜13-*.md` | 各ステージでやること・聞くこと・成果物の形式・完了条件 |
| 文章の指針 | `skills/cyrus/references/japanese-style.md` | 読みやすい日本語の書き方（lint のルールと対応） |
| CLI | `skills/cyrus/scripts/cyrus.py`, `cyruslib/` | 状態管理・完了条件の検査・認知負荷の検査・言葉遣いの検査・Lean の検査・記録の分類の表の集計（`tally`） |
| 表記の辞書 | `skills/cyrus/data/wording-rules.json` | ひらく漢字・表記ゆれの辞書 |
| 図表のスキル | `skills/visual-patterns/` | 図表を「読み取らせたいこと」から選び、描き、逆読みで確かめる手順（SKILL.md）。図表パターンのカタログの写し（`references/catalog/`）、索引（`data/index.json`）、描き方の対応（`data/render-routes.json`）、検査と描画のスクリプト（`scripts/vp_figure.py`） |
| サブエージェント | `agents/cyrus-*.agent.md` | 事実確認・論理批判・ペルソナ読者・拾い読み読者・照合判定（拾い読みと図表の逆読み） |
| コマンド | `prompts/cyrus.prompt.md`, `cyrus-status.prompt.md` | `/cyrus`, `/cyrus-status` |
| ルール | `instructions/cyrus-documents.instructions.md` | `documents/` を編集するときの約束 |
| フック | `hooks/cyrus-hooks.json` | 成果物を保存したら自動で検査／セッション開始時に進捗を知らせる |
| 依存（APM） | `apm.yml` の `dependencies.apm` | ステージ8の構成の選択に使う constructivism（asuka1975/constructivism）と、ステージ13の推敲に使う yomiyasu（nanaism/yomiyasu）。`apm install asuka1975/cyrus-harness` で cyrus を入れると、推移的に入る。中身はこのリポジトリに含めない（`.gitignore`） |
| 同期スクリプト | `scripts/sync-visual-patterns.py` | 図表パターンのカタログ（手元の研究リポジトリ visual-patterns）を `skills/visual-patterns/references/catalog/` に写し、`data/index.json` を作り直す（開発時だけ。PyYAML が要る） |

CLI は Python の標準ライブラリだけで動きます。Lean の検査には Lean 4（elan）が必要です。Vega-Lite の図を PNG にするのと、図表の逆読みには、`cyrus vision` と同じヘッドレス Chrome を使います。

## 半決定論的な設計

決定論で守れるものは CLI に任せ、判断と文章は LLM に任せます。両者は、次の3つの仕組みでつながっています。

1. **ゲート**: 各ステージの成果物を CLI が検査し、エラーがあれば次のステージに進めない（`cyrus advance` が拒否する）。
2. **フック**: 成果物を保存するたびに検査が走り、エラーが即座に Claude に返る。
3. **雛形**: 前のステージの成果物から、次のステージの雛形を決定論的に作る。判断が必要な箇所は TODO として残し、TODO が残る限りゲートは通らない。

| ステージ | 決定論（CLI） | 非決定論（LLM・サブエージェント） |
| --- | --- | --- |
| 1 目的 | 必須項目の有無、「伝えたいこと」の長さ | 聞き取り、1文の案づくり。ユーザーの承認 |
| 2 背景 | 必須項目の有無 | 資料の読み込み、聞き取り |
| 3 読者 | スキーマ、語彙の矛盾（知っている語と知らない語の重複）、読後の目的（purpose）と読む姿勢の値 | 読者像と語彙の聞き取り。ユーザーの承認 |
| 4 情報の選択 | 必須項目の有無、「集計できる素材」の表（同じ種類の記録が複数ある素材の登録）、「調べればわかること」の表（公開情報や手元の記録で確かめられる前提の登録） | 取捨選択 |
| 5 主張 | id の形式、参照の存在、循環の検出、支える主張の数、C0 のメッセージ種別（message_kind）、集計できる素材ごとに全件を数えた事実（`dataset`）があるか、調べればわかることごとに確かめる事実（`lookup`）があるか | 主張の木づくり。ユーザーの承認 |
| 6 事実確認 | 全事実の検証結果、出典の有無、反証された事実が前提に残っていないか、手戻りの一覧の公理に扱いがあるか（集められなかった記録だけなら警告）、集計の事実の `tally` を分類の表から数え直して照合、ユーザーの証言が「ユーザーにしか分からないこと」か「調べた事実つき」か | 調査・実験（cyrus-fact-checker。事実の確認、公理を支える証拠の探索と件数の集計、手元の道具での実験、記録の全件の分類）、人の判断を測る評価の問い、主張が頼る一般の事実の洗い出し |
| 7 論理 | Lean のコンパイル、証人による無矛盾性、印と形の門、確信度の計算、手戻りの一覧（確信度 0.4 未満・反対の証拠・［調査］で言い切れる水準に届かないもの）、手がかりの抽出、周の記録と打ち切り | モデルの設計（Planner）、Lean での記述（Writer）、敵対的な監査と確信度の引き下げ（Reviewer） |
| 8 構成 | constructivism の出力（08-structure.md）があるか、骨子の見出しがすべて節にあるか、構成チェックに未達の項目が残っていないか（警告）、genre・form・style があるか、全主張の割り当て、見出しの階層、節の数、結論を先に置いているか | 構成の選択（constructivism スキル）、節への主張と疑問の割り当て |
| 9 ストーリー | 節との対応、順序、メッセージの長さ、話の型が構成の型と合うか | メッセージとつなぎ。ユーザーの承認 |
| 10 詳細設計 | 表現の種類、図表の spec（根拠の形の目安、趣旨と候補、規模・精度・記法、描く手段）、1節あたりの新しい用語の数、字数と読了時間 | 見せ方の判断、図表の選択と作図判断（visual-patterns スキル） |
| 11 執筆 | 見出しが設計どおりか、図表が設計どおりか（キャプションに答えの一文、描き方、画像の有無）、文体、図表の参照 | 執筆、作図 |
| 12 認知負荷 | lint のエラーが0か、拾い読みの再現率が基準以上か、図表の逆読みに不一致・誤推論がないか、指摘すべてに対応したか | ペルソナ通読、拾い読み、図表の逆読み、照合判定 |
| 13 言葉遣い | 読者辞書に基づく検査、ひらく漢字・表記ゆれ、yomiyasu の検査（lint・diff）と記録の照合 | 推敲（yomiyasu スキル）。ユーザーの承認 |

## Lean による論理検証と確信度

ステージ7は、オーナーのフィードバック文書（このリポジトリには含めない）に従って作り直しました。仕様とオーナーの原則は、この文書ではなく、そちらと `.apm/skills/cyrus/references/owner-principles.md`（原則の原文）を見てください。ここでは実装の要点だけを書きます。

- 論証は、コンポーネントの宣言・関係公理・定理からなる Lean 4 のモデルとして書く（`07-logic/Argument.lean`）。すべての公理を定義に差し替えた証人（`Model.lean`）で、公理系が無矛盾であることを確かめる。
- Logical Model Planner・Lean Writer・Lean Logic Reviewer の3役で回す（`cyrus-logic-planner`・`cyrus-lean-writer`・`cyrus-logic-reviewer`）。2周目からは局所修正にし、`cyrus logic-round` が周の記録・差分と設計書の対応表・打ち切りの判定を受け持つ。
- CLI（`leancheck.py`）は、形と存在の検査（門）と確信度の計算だけを行う。命題かどうか、原子命題の数、証明が公理の名前だけかは、Lean のメタプログラムに問い合わせる。中身を数で近似するものは門にせず、`hints.json` に出して Reviewer にだけ渡す。
- 確信度は、証拠のない公理を 0.05 にし、主張の値は `@claim` 定理が依存する関係公理の最小値にする。0.4 未満の公理と `@against` の付いた公理、要ファクトが［調査］で 0.85（言い切れる水準）に届いていない公理は、ステージ6へ戻して証拠を集める。
- 主張の形（能力の文／比較の文）は、ステージ5でユーザーが選び、05-claims.json の `form` に書く（必須）。比較の文があるときだけ、ステージ7で確率の世界を作る。
- ステージ7の終わりに、手戻り（調査・実験）を済ませてから、確信度を左右する弱い前提（`report.json` の `weak_premises`）を、調べた範囲を添えて日常語で5つまで見せ、1問だけ聞く。調べる前に「証拠がない」とは言わない。
- 手戻りの一覧はステージ6で受け取り、公理ごとに調査・実験・ヒアリングで事実を集める（事実の `axioms` に公理の名前）。明らかな誤りは `07-logic/rejected.json` に記録して棄却する。事実が集まった公理は、ステージ7で名前を変えて新しい公理として書き直す（Reviewer は値を下げるだけなので、確信度を上げる道はこれだけ。オーナーの決定）。
- ステージ11では、弱い前提を本文に条件として書き、確信度 0.4 未満の主張は主張として書かない。

### 調べれば分かる前提が、調べられないまま 0.05 で残る問題（2026年10月の直し）

実際の文書3件と例（`docs/ai-notes/examples/git-branch-rules`）を調べたところ、手戻りの一覧が出ても実行されず、主張の中心が確信度 0.05（仮説扱い）のままステージ8へ進んだ文書が2件あった。例では `approver_not_author`（要ファクトは「GitHub Docs で確かめる」）が調べられないまま残り、C0・C3 が仮説扱いになっていた。原因は、ステージ6が調べないことではなく、調べれば分かる事実が検証の対象にならない経路にあった。

- 事実の一覧はステージ5でユーザーの資料から作られ、ステージ6はそれだけを確かめていた。論証が頼る一般の事実（道具の仕様、研究で分かっていること）は、ステージ7で【仮定】として現れるまで事実にならなかった。ステージ4の「調べればわかる」の印にも、拾う手順がなかった。
- ステージ7→6の手戻りは、`advance` のときに何も警告されず（GT058 は戻ったあとにしか出ない）、ガイドにも「このまま進める」の逃げ道があった。
- 要ファクトは Writer が実験やヒアリングの形で書きやすく、ステージ6の手戻りの表でも調査は最後にあり、fact-checker には「命題の証拠を探す」仕事がなかった。

直したこと:

- ステージ5で、主張が頼る一般の事実も F に挙げる（04 の「調べればわかる」の印を拾う）。ステージ6の最初に、05 にない一般の事実を `cyrus-fact-checker` に探させて登録する（事実の `claims` に支える主張の id。GT051 はこれを 05 にない事実として警告しない）。読者像の能力は `user_asserted` で登録してよい。
- 要ファクトの先頭に集め方の札 `[調査]`／`[実験]`／`[ヒアリング]` を付ける（Planner が決め、Writer が写す。Reviewer は札の妥当性も見る）。CLI は `report.json` の `rework`・`weak_premises` に `how` と `need` を出す。札がなくても読める（古い文書を壊さない）。
- 手戻りの一覧に扱い（事実の `axioms` か `rejected.json`）のない公理が残っているあいだ、`cyrus lean`／`check` が警告 LG040 を出す（集め方ごとの数つき）。ステージ7を `advance` で出るには `--accept-warnings` が要るので、集めずに進む判断が記録に残る。
- ステージ6の手戻りは、調査 → 実験 → ヒアリングの順にし、`[調査]` の公理は1回の fact-checker 呼び出しにまとめて渡す（仕事 B）。「このまま進める」は、調査を済ませたあとの実験・ヒアリングの公理にだけ使える。
- `cyrus-fact-checker` に仕事 B（公理の名前・日常語の命題・要ファクトを受け取り、支える事実と反対の事実を文にして返す。見つからなければ探した範囲を `not_found` に返す）を足した。

### 事実が1件の事例や発言の切り抜きになり、記録を数えない問題（2026年10月の直し）

実際の文書で、素材に同じ種類の記録が十数件以上あっても（取材メモの19のエピソード、別の文書の確認の質問の一覧）、事実は「印象に残る1件」や「筆者は〜と答えた」という発言の切り抜きになり、「n 件中 m 件が A」という分布の事実が作られていなかった。ステージ4の分析には「どれも同じ型。1つの話を深く書くほうが伝わる」と書かれ、残りの記録は載せない情報に回っていた。傾向・頻度・原因の主張（「破綻の原因は3つ」）が、1件の事例と発言の引用で支えられ、論証がデータを網羅していなかった。

原因は、記録の集まりを「数える対象」として扱う場所が、どのステージにもなかったことにある。ステージ4は素材から要点を抜き出すだけで、ステージ5の事実は「検証できる一文」の形しか示しておらず、ステージ6の fact-checker には「確かめる」「探す」の仕事しかなかった。発言の記録は、発言が記録にあれば `verified` になり、そのまま内容を述べる公理の `@support` に使われていた。

直したこと（分類は LLM、数えるのは CLI という半決定論の分担）:

- ステージ4の `04-analysis.md` に「集計できる素材」の節を足した（必須。表で名前・単位・件数・置き場所・数える観点。なければ「なし」）。ステージ2では、記録が複数あるなら代表の数件でなく全件をもらう。
- ステージ5では、表にある素材ごとに全件を数えた事実（`dataset`）を1つ以上挙げる（ないと GT045 の警告。表にない名前は GT046 のエラー）。傾向・頻度・原因の主張は数えた事実で支え、1件の事例は「起きうる」ことしか支えない。発言の記録は、発言があったことの事実であって内容の根拠ではない。
- ステージ6では、`cyrus-fact-checker` の仕事 C（記録を分類して数える）が全件を1件1行の表（`02-context/tally-<名前>.md`。「分類」の列）に分類し、`cyrus tally` が数える。事実には `tally`（`items`・`total`・`counts`・`criteria`）を書き、門が表を数え直して照らす（合わなければ GT152 のエラー、04 の件数と違えば GT153 の警告。`tally` がなければ GT150、表が読めなければ GT151）。割合や件数を述べる事実に数え方が残っていないときは GT154（参考）。
- ステージ7では、集団についての公理（傾向・頻度・原因）の `@support` は数えた事実にし、1件の事例は存在の公理しか支えない。発言の記録の事実は内容を述べる公理を支えない（Planner の設計の手順、Reviewer の監査項目 6a・6b）。
- ステージ10では `tally` の `counts` が図表の値になり、ステージ11では件数と割合を先に書き、数え方を添え、そのあとに例を1つ書く。

### 調べれば分かる前提が「ユーザーの記憶」として残り、実験が設計されない問題（2026年10月の直し）

0.2.2（上の2つの直しを含む）で書いた実際の文書で、次のことが起きた。

- ユーザーが「よくある言い方だ」「定番の言い回しだ。検索すればいくらでも出てくる」と言った前提が、Planner で【仮定】＋［ヒアリング］になり、オーケストレータは調べる前に「あなたの記憶だけが根拠です」「仮説として書きます」とユーザーに伝えた。ユーザーが押し返して初めて fact-checker が検索した。見つかった2件の指摘は、文字列そのものの名指しがないという理由で `partially_verified` にとどまり、Planner は案を 0.5 に置いた。
- ［調査］の要ファクト（「コーパスで頻度を確かめる」「手元のセッションのログを検索する」）が付いた公理が 0.5〜0.55 にあり、手戻りの閾値 0.4 を超えていたため一度も調べられず、主張の中心の第2の定理と、別の主張の言い切りの強さを下げたままになった。手元のログを数えれば1分で済む調査だった（あとで数えたところ、手元にある 402 のプロジェクトの記録のうち、その実験のプロジェクト以外で Claude がその言い回しを自発的に書いていたのは、別のプロジェクトのレビューの出力の1件だった）。
- ［実験］の要ファクト（「AI の実際の出力を集めて分類する」）と、人の判断で決まる要ファクト（「同じ語のペアで自然な文と不自然な文を1組ずつ挙げてもらう」）は、設計も試行もされなかった。後者はユーザーに「例を思いつきますか」と聞いて「思いつかない」で終わった。評価してもらう項目をこちらで用意すれば測れることだった。
- ステージ7の最後の周で、オーケストレータはステージ6に戻らず、07 の中で 06-facts.json に「集められなかった」の `unverified` の事実（notes に「実施していない」）を書いて一覧を消し、`--accept-warnings` なしで先へ進んだ。LG040・GT058 は、`axioms` のある事実なら status を問わず「扱いあり」としていた。
- 04 の「不足している情報」に「調べればわかる」と印の付いた3項目は、05 の事実にならず、ステージ6で調べられなかった。印を拾う手順はガイドの文だけで、機械は見ていなかった。

直したこと:

- ステージ4に「調べればわかること」の表（名前・確かめること・当たる先。なければ「なし」）を足した（必須の節）。ステージ5で、表の項目ごとに確かめる事実（`lookup`）を挙げないと警告（GT048。表にない名前は GT049）。広く共有されているか（よくある言い方か、多くの人が同じ経験をしているか）も、辞書・コーパス・検索・手元の記録で数えて確かめる項目として、ここに登録する。
- ステージ6に「数えて確かめる命題」（意味の裏付けと頻度の裏付けを分け、目安を先に決め、文字列の不一致だけで下げない）、「実験を設計して行う」（設計 → 手元の道具で実行（fact-checker の仕事 D）→ 手元にないものが要るときだけユーザーに頼む）、「人の判断を測る（評価の問い）」（判定してもらう項目をこちらで用意し、1回で聞き、`tally` の事実にする）を足した。
- `user_asserted` の事実は、ユーザーにしか分からないこと（`private: true`）か、同じ内容を調べた事実の id（`checked`）を持つ（GT156・GT157）。世の中についての証言を、調べずに証言のまま残さないため。
- 手戻りの一覧に `research` の理由を足した: 要ファクトが［調査］で、確信度が 0.85（言い切れる水準）に届いていない公理は、閾値 0.4 に関係なく一覧に入る（調査はユーザーの手を借りずに済む）。調査を尽くした公理を書き直すときは、［調査］を残さない。
- 集められなかった記録（`unverified` の事実）だけで扱った公理と、調べ残しのある［調査］の公理（`verified` の事実がまだない）は、扱いなしとは別の警告にした（LG041・GT155）。ステージ7を出るにもステージ6を出るにも `--accept-warnings` が要り、ユーザーが進めると決めたことが履歴に残る。［実験］は設計を書いて試す前に、［ヒアリング］は尋ねる前に、「集められなかった」にしない。調べ尽くした［調査］は、Planner が公理を書き直すときに要ファクトから外す（ガイドで決めていることで、CLI は見ていない。名前を変えた公理と古い `axioms` のずれは GT059 が出す）。
- ステージ7の終わりの順を、手戻り（調査・実験）→ 弱い前提を見せる（調べた範囲を添える）→ ヒアリング、に改めた。調べる前に「証拠がない」「記憶だけが根拠」と言わない。ステージ7の中で「集められなかった」を書いて一覧を消さない。
- Planner は、ユーザーの「多くの人がそう感じる」「定番だ」を【経験則】＋［調査］（目安つき）にし、人の判断で決まる前提は「項目を用意して判定してもらう」［実験］にする。`@confidence` の案を支える事実の値より低くするときは理由を書く（Reviewer の監査項目 20・21）。

## 認知負荷の検査

`docs/ai-notes/deep-research.md` の特徴群のうち、形態素解析の道具なしで計算できるものを実装しました。

- **文・語（短期記憶）**
  - 文の長さ、読点の数、読点のない長い文
  - 漢字の連続と割合、二重否定、括弧の長さと入れ子
  - 1節あたりの新しい用語の数
- **構造（中期記憶・見通し）**
  - 段落の長さ、段落頭の指示語、「後述」などの遠い参照
  - 見出しの階層・長さ・形の揃い、最上位の節の数、小見出しのない長い節
  - 箇条書きの項目数と入れ子、表の大きさ、図表の参照
  - 文体の混在、同じ文末の連続、推定読了時間
- **視覚（中心視野・周辺視野）**: `cyrus skim` が次の3つのビューを作ります。
  - outline: 見出しと段落の最初の文。頭だけ読む拾い読みを模します。
  - pickup: ひらがなを落とし、漢字・カタカナ・英数字だけを残します。周辺視野で目に飛び込む語を模します。
  - local: 各段落を焦点にし、前後の段落をぼかします。

拾い読みのテストでは、原稿を見ていないサブエージェントがビューから内容を再構成します。別のサブエージェントが、それを意図（ストーリーのメッセージ）と照合します。再現率が70%未満なら、次に進めません。テストした原稿の指紋（ハッシュ）も記録するので、テストのあとで原稿を直した場合は、テストをやり直さない限り次に進めません。

### 画像での拾い読みテスト（別のモデル）

テキストのビューでは、見出しの大きさ、太字、図、余白、表やコードの囲みといった「見た目」が抜け落ちます。そこで `cyrus vision` で、原稿を実際の画面の見え方で検査します。

1. Markdown を HTML にし、目が留まりやすい箇所に「注視点」の印を付ける。見出し、段落の最初の文、太字、箇条書きの頭、表の見出し行、図とキャプション、コードの1行目、囲み枠の最初の文が対象。Mermaid の図は実際に描画する。
2. ヘッドレス Chrome で、読者の媒体（画面・スマホ・印刷・スライド）に合わせた幅で描き、注視点の位置を取り出して、全体を画像にする。
3. Pillow でぼかす。注視点はくっきり、その左右（傍中心視野）は少しぼかし、それ以外（周辺視野）は読めないほどぼかす。傍中心視野は横に広く、縦には行をまたがない。
4. 一画面ずつに切り分け、全体の縮小図（一瞥の見え方）も作る。
5. 画像だけを一時ディレクトリに移し、読み手（既定は `agy` 経由の Gemini）に読ませる。読み手は、全体の要約、節ごとの理解、見た目の問題（目立たなかった重要な点など）を JSON で返す。
6. 照合判定のサブエージェント（Claude）が、意図したメッセージと照合する。

既定の読み手を Gemini にしたのは、原稿を書いた Claude が読み手も演じる偏りを避けるためです。

読み手のコマンドは、プロジェクトのルートの `cyrus.config.json`（`vision.reader`）で変えられます。コマンドと引数のリスト、起動するときに設定する環境変数（`null` で消す）、モデル名、待つ秒数を書きます。引数には `{prompt}`（なければ標準入力で渡す）、`{workdir}`、`{schema}`、`{schema_file}`、`{model}`、`{timeout}` の置き換えを書けます。回答は標準出力から読み取り、agy や Claude Code の JSON 出力、回答の JSON だけ、文章の中の ```json の囲み、のどれにも対応します。`cyrus vision --show-command` で、起動せずに組み立てたコマンドを確かめられます。書き方の詳細は `stages/12-cogload.md` にあります。

既定の `agy` は、権限確認を省略せず、読み取り専用の plan モードで起動します。ヘッドレスでは、確認が必要な操作（シェルコマンドなど）は自動で拒否されます。`agy` の `--sandbox` はファイルの読み取りを制限しなかったので、原稿を読ませない隔離は置き場所で行っています（画像だけを無関係な一時ディレクトリに置き、原稿のパスは渡さない）。この置き場所での隔離は、どの読み手でも cyrus が行います。読み取り専用で起動することは、設定ファイルのコマンドの書き方に任せています。

テキストのテストと同じく、原稿の指紋が一致しない結果では完了条件を満たしません。Chrome か読み手のコマンドがない環境では、理由を書けば省略できます。使える環境では省略できません。

基準の値は、読者の知識のレベルと、読む状況によって変わります。たとえば初心者向けなら文を短めに、スマホで読むなら段落を短めにします。

## 構成の選択（constructivism）

ステージ8の章立ては、constructivism スキル（asuka1975/constructivism。日本語文書の構成を、読者の目的・読む姿勢・メッセージ種別から技術文書・学術・ビジネス文書のカタログで選ぶ）に任せます。cyrus の依存として APM で一緒に入ります。追従している版は `apm.yml` の `dependencies.apm` にあります（2026年10月時点で v1.0.1）。

- constructivism の入力は、cyrus の成果物から渡します。読者の目的（`03-reader.json` の `purpose`）と読む姿勢（`reading_mode`。冒頭だけ読む決裁者のために `headline` を足した）、メッセージの種別（`05-claims.json` の C0 の `message_kind`）は、このために成果物に加えた項目です。どちらも列挙型で、ゲートが値を検査します。
- v1.0.1 から、目的は必須で、メッセージと内容はスキルが創作して補いません（既定値があるのは専門性・読む姿勢・社内外と媒体だけ）。cyrus 側では、`purpose` をゲート（GT029）で必須にしているので目的は必ず渡り、メッセージ（C0）と内容（04-analysis.md と主張の木）はステージ8より前に確定しているので、スキルに補完を求められることはない設計です。
- 出力（構成選択結果・骨子・構成チェック）は `08-structure.md` にそのまま保存し、`08-structure.json` には `genre`（採用構成）・`form`（型）・`style`（文体）と、骨子から作った節を書きます。ゲートは、骨子の番号付きの見出しがすべて節にあること（GT073）、3つの項目があること（GT074）、スキルが入っていること（GT071）を確かめます。
- 構成チェックは、v1.0.1 からスキルの最終チェックの6項目を同文で `- [x]`／`- [ ]` に並べ、各項目に「判定理由」の行を添える形です。ゲートは項目の文言をスキルの版に結び付けず（版が上がるたびに壊れるため）、未達（`[ ]`）の項目があることと、項目が1つもないことだけを警告します（GT075）。構成チェックの文言が入っている版と合っているかは、テスト（`tests/test_cyrus.py` の HarnessConsistencyTest）が fixture と入っている SKILL.md を突き合わせて確かめます。
- `form` はステージ9の話の型になり（GT088）、`style` はステージ11で本文の文体と照合します（GT118）。`genre` はステージ13で yomiyasu の文書の種類に写します。
- 2026年10月時点の例（`docs/ai-notes/examples/`）は、この統合と、図表（visual-patterns。`spec` と逆読みの結果）の統合より前の形式です。`purpose`・`message_kind`・`genre`・`form`・`style`・`08-structure.md`・図表の `spec` はありません。

## 図表（visual-patterns）

図表は「読み手に何を読み取らせたいか」から選びます。手順は、オーナーの図表パターンのカタログ（visual-patterns。手元の研究リポジトリ）の選択手順そのもので、スキル `visual-patterns` の SKILL.md にまとめてあります。カタログ本体（taxonomy.md・index.yaml・パターン文書）は `scripts/sync-visual-patterns.py` で写し、本体は書き換えません。趣旨・候補・意図の型を増やすのはカタログの側（逆読みの失敗から）で、スキルの側では増やしません。カタログの開発の記録（fixtures・adr・development.md）は写しません。

ステージごとの分担は次のとおりです。

| ステージ | カタログの手順 | 決定論（CLI） | 非決定論 |
| --- | --- | --- | --- |
| 10 見せ方 | 手順1〜7（伝達目標、根拠の形で文章か図表かを決める、趣旨、候補、制約、組み合わせ） | spec の検査（`vp_figure.py check`）。根拠の数が手順2の目安に満たなければ図表にしない（VP020）、根拠の形から選べない趣旨（VP031）、候補にないパターン（VP041）、規模・精度・記法の制約（VP050〜052）、描く手段（VP071 手段なし・VP072 Chrome なし・VP073 描き方の注意・VP074 render の不一致） | 答えと根拠の書き出し、趣旨とパターンの選択、作図判断 |
| 11 書く | 手順8（作図） | 設計との照合（GT113〜117）: 図表があるか、キャプションが答えの一文か、描き方が spec どおりか、PNG があるか。設計にない図表はエラー。ステージ13でも final.md に同じ照合をかけ、推敲でキャプションが変わっていないことを確かめる | Mermaid か Vega-Lite の仕様を書く |
| 12 認知負荷 | 手順9（逆読み・削除の問い） | 図表だけを一枚ずつ画像に切り出し、読み手に渡す（`cyrus figure read`。枚数が多ければ分けて渡す）。結果と原稿の指紋（本文・画像の中身・設計の答え）を照合し、設計の図表ごとに読み手の回答と判定があるかを確かめる（GT150〜157） | 読み手（別のモデル）が主張を一文で書く。判定者（cyrus-alignment-judge）が答えと照らす |

- **spec** は、図表ごとの「問い・答え（一文）・根拠（形と数）・精度・読み方・趣旨・パターン・作図判断・描き方」です。答えは `09-storyline.json` のメッセージ、根拠は主張と事実から取ります。図表は根拠の形を見せ、答えはキャプションが言う、というカタログの分担をそのまま形にしています。手順2の目安に満たない根拠は VP020 で止めますが、カタログの「根拠を文章で書き出し、同じ文型が3つ以上並ぶ、または読み手が前の文に戻って照合し直すなら図表」の判断は `evidence.below_threshold_reason` に記録すれば通します（警告に下がる）。精度 exact に対する概観のパターンは VP053 で止めます。
- 原稿の指紋は、テキストの拾い読みテストでは本文のハッシュですが、画像のテストと図表の逆読みでは、参照する画像ファイルの中身（`assets_hash`）と設計の答え（`figures_hash`）も含めます。本文を変えずに PNG や spec.answer を差し替えても、記録は失効します。
- **描き方**は2通りです。diagram 系は Mermaid で本文に埋めます。chart 系は Vega-Lite の仕様（`figures/fig-NN.vl.json`）を書き、`cyrus figure render` がヘッドレス Chrome で PNG にします（`cyrus vision` と同じ仕組み。ライブラリは CDN から読み込み、原稿は送らない）。パターンごとの描く手段と忠実度は `data/render-routes.json` にあり、ヘッドレス Chrome で実際に描けることを確かめた上で登録しています。
- **逆読み**では、読み手にキャプションも本文も答えも渡しません。読み方が参照の図表にだけ、問いを先に示します（カタログの development.md の条件）。読み手が「文章のほうが読みやすい」と答えたら削除の問い（手順9）として知らせ、削るかどうかは書き手が決めます。判定（match / partial / mismatch / misread）は、カタログの判定者の基準（一致＝答えの主張が読み取りに含まれる、答えにない詳細は数えない、図にない意味は矛盾か追加の主張だけ）をそのまま使います。
- カタログの評価の条件と、ハーネスが意図して変えている点が3つあります。(1) 読み手に、読者ペルソナの役割・背景・知識の程度を渡します（`cyrus vision` と同じで、想定読者として読ませるため。答えや動機は渡しません）。(2) 作り直した図も、直していない図も、同じ読み手が同じ題材で読み直します（カタログは、作り直した図は別の読み手か別題材で確かめ、同じ図は同じ読み手に二度読ませない、としていますが、ハーネスでは読み手を替えられません）。(3) 読み手に出典とパターン名を渡しません（カタログは案内に「出典とパターン名だけ」を書きます）。読み手が LLM なので、パターン名が主張の形を先に知らせることになるためです。記法の知識は spec の検査（VP052）と読者の知識の程度で扱い、戸惑いは unclear で拾います。判定者には、カタログと同じく、答え・精度・作図判断に加えて図に描いた要素（draft.md の Mermaid・表、Vega-Lite の仕様）を渡します。
- 会話の記録で提案された「役割」の軸（地図・証拠・対比・参照・定義）は、カタログで採用されていないので、スキルにも入れていません。カタログの検討中の趣旨（差分・状態変化・並列など）も、選べる経路にしていません。

## 言葉遣いの検査

読者ペルソナの語彙（知っている語・知らない語・避けるべき語）を辞書として扱います。

- 知らない語が、初出で説明されずに使われていればエラーにする。説明が初出より後にある場合もエラーにする。
- 避けるべき語が使われていればエラーにする。
- 辞書にないカタカナ語と英字語は「判断が必要な語」として知らせる。判断の結果は辞書に追加するので、使うほど辞書が育つ。
- ひらく漢字と表記ゆれは `data/wording-rules.json` の辞書で検出する。

推敲（不自然な比喩、あいまいな主述関係、硬い表現、冗長な言い方、立場に合わない文末や敬語）は yomiyasu スキルに任せます。yomiyasu は表記をそろえない（補助動詞と形式名詞「事」「為」を除く）ので、表記の検査は cyrus に残しています。yomiyasu は推敲した最終稿に lint と diff をかけ、最終稿のハッシュを記録に残します。ステージ13の完了条件は `yomiyasu_check.py verify` で、final.md が draft.md から推敲して検査した本文のままかを確かめます（GT133・GT134）。

## 既知の限界と今後の候補

- 日本語の解析は文字種のヒューリスティクスです。GiNZA や Sudachi を使えば、係り受けの距離や語彙の難易度も測れますが、依存関係が増えます。
- 見た目の検査は、画像を別のモデルに読ませる非決定論の方法だけです。視覚的な煩雑さ（clutter）などを画像から数値で測る決定論の指標は、まだありません。
- Mermaid の図の描画には、CDN（jsdelivr）からライブラリを読み込みます。原稿は送りません。オフラインでは図がソースのまま表示されます（`CYRUS_MERMAID_JS` でローカルのファイルを指定できます）。`cyrus figure render` と `cyrus figure read` の描画（Mermaid と Vega-Lite）も CDN から読み込み、`VP_MERMAID_JS`（`CYRUS_MERMAID_JS` も使う）と `VP_VEGA_JS` でローカルのファイルを指定できます。
- 主張と本文の文との対応は機械的に取っていないため、hedge を守っているかは LLM の判断に任せています。
- 図表の組み合わせ（一つの図番号に複数のパターンを入れる Composition）は、カタログで未定義なので、図を分けて扱います。Vega-Lite で描けない地図系のパターンは、描く手段が「近似」か「なし」です（`render-routes.json` の fidelity）。
- 図表の逆読みの読み手は、`cyrus vision` と同じ別のモデルです。読み手が一人しかいないときの偏り（カタログの adr/0023）は、ハーネスでは解けません。
- `apm install` は、以前に展開したフックを settings.json から自動では消しません。フックを変えたら確認してください。
