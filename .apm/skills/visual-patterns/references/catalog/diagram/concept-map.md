# コンセプトマップ

## 定義

概念をノードに置き、関係を線で結び、線に関係の種類を書き添えた図である。ノードとラベルを続けて読むと「A は B の一種である」のような命題になる。一般的な概念を上、具体的な概念を下に置くことが多い。

## 目的

読み手が「この概念は何と、どういう種類の関係で結ばれているか」に答えられるようにする。

## どういうときに利用するか

- 用語集や領域の語彙で、概念同士の関係の種類（包含・利用・前提）を示したい
- 関係が多対多で、文章にすると前後の参照が頻発する（手順2 の「段階・主体・部分とその関係」の行）
- 関係の全体像を先に見せ、個々の定義は本文に委ねたい

## どういうときに利用してはいけないか

- 関係に原因から結果への向きがあり、その連鎖が主題である
- 関係の種類が一つしかなく、箇条書きで足りる
- 定義や条件を正確に読ませたい。線のラベルは短く、条件を載せられない
- 遠目に見るスライドなど、線のラベルが読めない媒体に出す

## 入力の構造

graph: categorical。ノードが概念、辺が関係で、辺が関係の種類を持つ。向きは問わない。

```yaml
nodes: [趣旨, 情報構造, パターン]
edges:
  - {from: 趣旨, to: 情報構造, label: 前提とする}
  - {from: 趣旨, to: パターン, label: 候補を持つ}
```

## デザインの文法

- 関係は線で結び、線の途中か脇に関係の種類を書く。向きのある関係だけ矢印にする
- 一般的な概念を上、具体的な概念を下に置き、位置で抽象度を読ませる
- 関連の強い概念を近くに置き、近接でまとまりを示す
- 線の交差を減らし、ラベルが線や他のノードと重ならないようにする

## 作成時のルール

- 一つのノードには一つの概念を置き、文を書かない
- 辺のラベルは動詞か短い句にし、ノード・ラベル・ノードで命題として読めるようにする
- 主題の概念を一つ決め、そこから辿れる範囲にノードを絞る
- 図から読み取ってほしい命題を、本文かキャプションに一文で書く

## やってはいけないこと

- 関係の種類を書かずに線だけで結ぶ
- 上下の位置に意味がないのに縦に並べ、階層を示唆する
- 原因と結果の連鎖を向きのない線で結び、因果の主張をぼかす

## 利用例

- Semantic network。用語集の語彙が「一種である」「部分である」の関係でどうつながるかを示す
- 分類体系の導入。趣旨・情報構造・パターンがどう関係するかを一枚で示す

## NGパターン

- ラベルのない線で全体を結ぶ。関連があることしか伝わらず、関係の種類が読めない
- ノードに説明文を書く。構造より読解の負担が大きくなり、図にした意味がなくなる
