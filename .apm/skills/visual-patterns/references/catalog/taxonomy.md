# 図表のパターン分類体系

## 1. 対象範囲と選択原則

### 1.1 対象範囲

本カタログは、文書内で情報の理解を補助する視覚表現を対象とする。

対象には以下を含む。

- データを視覚的に表現するチャート
- 概念・関係・構造・処理を表現するダイアグラム
- 対象の外観や具体例を示す画像
- 行列構造によって情報を整理する表

装飾のみを目的とし、情報を伝達しない画像は対象外とする。

### 1.2 伝達ギャップと認知コスト

表現を選ぶ目的は、
読み手に持ち帰ってほしい内容（伝達目標）と読み手が実際に持ち帰る内容の差（伝達ギャップ）を、できるだけ少ない認知コストで小さくすることにある。

文章も図表も読み手に認知コストを課す。違うのはコストの種類である。

| 表現 | 読み手が払うコスト | 起きやすいギャップ |
| --- | --- | --- |
| 文章 | 処理コスト: 量を読み、一列に並んだ記述から構造を組み立て直す | 欠落: 読み飛ばす、構造を組み立てきれない |
| 図表 | 推論コスト: 符号化を解読し、抽象化で省かれた部分を補う | 誤推論: 省かれた部分を誤って補う、意図しない意味を読み取る |

文章で理解に失敗した読み手は、たいてい失敗を自覚する。
図表を誤読した読み手は、誤読を自覚しにくい。
このため、図表を使うときは文章を添え（1.4）、
誤読の余地を手順5〜6 のパターンの選択と手順8 の注釈で狭める。
この非対称は図表に文章を添える理由であり、図表を避ける理由ではない。

### 1.3 表現の連続体

表現は文章と図表の二択ではなく、抽象度の連続体をなす。

散文 → 箇条書き → 表 → チャート・ダイアグラム

右へ進むほど処理コストは下がり、推論コストは上がる。
箇条書きも抽象化の一つであり、
項目間の関係（理由・順序・対立）の推論を読み手に任せている。

どこまで右へ進むかは、答えではなく根拠の形で決める（手順2）。
答えは常に一文で書く（手順1）ので、答えが一文で言えることは左を選ぶ理由にならない。

外観を示す画像はこの連続体の外にあり、手順2 の「外観」の行で判断する。

### 1.4　文章と図表の分担

図表は根拠の形を見せ、文章は答えを言う。図表を使う場合も、文章を添えて推論コストを下げる。

- 図表から読み取ってほしい答えを、本文またはキャプションに一文で書く
- 条件・例外・否定・理由・不確実性は文章が担う。
  答えがこれらを含むことは図表を避ける理由にならない。図表は根拠を見せ、条件や理由は添え書きが言う
- 抽象化で省いた情報のうち答えに要るものは、添え書きで補う
- 同じ情報を同じ粒度で両方に書かない（読み手は両方のコストを払う）

## 2. 選択手順

図表は「読み手に何を読み取らせたいか」から選ぶ。
表現形式（文章か図表か、チャートか表か）から選び始めない。

本書の軸は、選択の入力（3章）と、
選ばれたパターンを説明する記述属性（4章）に分かれる。

| 手順 | 問い | 参照 |
| --- | --- | --- |
| 1. 伝達目標 | 読み手は何を問い、何を持ち帰るべきか | 本章 |
| 2. 表現の決定 | 根拠の形は図表にする目安に当たるか | 本章、1.2〜1.4 |
| 3. 趣旨 | その問いはどの型か | 3.1 |
| 4. 情報構造 | 手元の情報は、その趣旨の前提を満たすか | 3.2 |
| 5. 制約 | 候補は規模・精度・読者・出力媒体に合うか | 3.3 |
| 6. 候補の決定 | 残った候補のどれを使うか | index.yaml |
| 7. 組み合わせ | 一つのパターンで足りるか | 5章 |
| 8. 作図 | 答えの主張をどう図の形にし、どの手段で運ぶか | 本章、パターン文書 |
| 9. 検証 | 実際に伝わる内容は伝達目標と一致するか | 本章 |

手順2で文章を選んだ場合は、手順3〜8を飛ばして手順9に進む。

### 手順1: 伝達目標を書く

表現を決める前に、次の五つを書き出す。

- 問い: 読み手がこの箇所で答えを得たい問い
- 答え: 読み手に持ち帰ってほしい主張を一つ、一文で。
　　参照用の情報なら、何を探し当てればよいか
- 根拠: 作者がその答えを支えるために同じ文書に示したもの。
　　値の集まり（項目・時点・地点ごとの値）、項目と属性、段階・主体・部分とその関係、条件と結果、外観のどれか。
　　読み手が答えを受け入れる、確かめる、自分の場合に当てはめるのに要るものを、数を添えて書く
- 精度: 正確な値が要るか、大小・傾向・形がわかれば足りるか
- 読み方: 通読して理解するか、必要な箇所を探して参照するか

この答えを意図と呼ぶ。
問いの型（趣旨、3.1）は数に限りがあるが、意図は場面ごとに異なり、数に限りがない。
意図は本書には書かず、パターン文書の「意図の型と手段」（6.3）で手段に結びつける。

答えを一文でかけない場合は、表現を選ぶ前に内容を整理する。
内容に主張が複数ある場合は、主となる一つを答えにし、
残りは手順7 の組み合わせかキャプションに回す（adr/0006）。
根拠は一文にまとめない。手順2 は根拠を見る。

問いが複数ある場合は、主となる一つで手順6まで進め、
残りは手順7で扱う。

### 手順2: 根拠の形で表現を決める

手順1 の根拠を次の表に当てはめる。
当たる行があれば図表を候補とし、手順3 でその行の趣旨のカテゴリの中から趣旨を選ぶ。
どの行にも当たらなければ、文章で書く（箇条書きを含む）。
答えが一文で言えること、答えが条件・理由・否定を含むことは、文章を選ぶ理由にならない（1.3、1.4）。

| 根拠の形 | 図表にする目安 | 趣旨のカテゴリ（3.1） |
| --- | --- | --- |
| 量: 項目・時点・地点ごとの値 | 答えが述べる対象の値が 5 つ以上（例: 5 項目、3 時点 × 2 系列。同じ表にあっても答えが触れない区分の値は数えない）。または、2 つ以上の区分（群・条件・項目）を 2 つ以上の時点や条件で比べる増減・差（2 × 2 以上）が答えで、差の大きさが精度に含まれる。値の大小・増減・割合・順位・分布・ばらつき・相関が答えを支える | 比較・変化・構造（構成）・分布・空間・関係（相関）・プロセス（流量） |
| 項目 × 属性: 複数の対象を複数の観点で述べる | 対象 2 つ以上 × 観点 3 つ以上、または対象 5 つ以上 × 観点 2 つ以上。読み手は知りたい対象や観点を探して参照する、または二つの観点で対象を位置づける | 比較（属性比較・位置づけ）・参照（値検索） |
| 段階・主体・部分とその関係 | 主体や部分が 2 つ以上あり、その間の関係（受け渡し・所属・層・依存・因果・対立）が答えを支え、主体・部分と、その間の段階（受け渡し・処理・変化。一本の受け渡しを一つに数える）を合わせて 4 つ以上。または数によらず、分岐・合流・循環・多対多・入れ子を含む。または出来事の前後関係が答えで、期限や時点が別の出来事からの相対で決まる。または、何かが主体から主体へ渡るたびに減る・変わることが答え（主体が同種で、受け渡しが同じ規則の繰り返しでもよい。値は要らない） | プロセス・構造・関係・変化（経緯） |
| 条件と結果 | 条件が 2 つ以上あり、どの条件に当たるかで結果が分かれる | 参照（条件判定） |
| 外観 | 形状や見た目が答えで、言葉では一意に特定できない | 実物 |

文章にするのは、根拠が次のどれかにとどまるときである。

- 値が 4 つ以下の比較や増減（一項目の二時点、二項目の大小。2 つ以上の区分を 2 つ以上の時点や条件で比べ、差の大きさが精度に含まれるものを除く）
- 一つの定義、一つの理由、または条件がすべて揃って結果が一つに決まる規則
- 主体が一つで分岐のない段階（数によらず番号付きリスト）、主体・部分と段階を合わせて 3 つ以下の直線、または 3 つ以下の項目の列挙（主体から主体へ渡るたびに減る・変わることが答えの連鎖を除く）

迷う場合は、根拠を文章で書き出す。
同じ文型の文が 3 つ以上並ぶ、または読み手が前の文に戻って照合し直すなら図表にし、そうでなければ文章にする。

目安の数は初期値である。手順9 の削除の問いの答えで改める。

図表にする場合、次を手順3〜8 に引き継ぐ。

- 条件・例外・否定・理由・不確実性は添え書きが担う（1.4）
- 符号化が読み手の慣習になく凡例の学習を要する、配置・矢印・大きさ・色が意図しない意味を示唆しうる、
  正確な値が要るのに位置や長さからしか読み取れない、図表だけではどこに注目すればよいか分からない:
  手順5〜6 でそれを避けるパターンを選び、残りは手順8 の注釈で解消する。
  解消に図表より長い説明が要るなら、表か構造化した文章にする

### 手順3: 趣旨を決める

手順1 の問いを 3.1 の趣旨に当てはめ、手順2 で当たった行のカテゴリの中から、主となる問いの趣旨を一つ選ぶ。

### 手順4: 情報構造を確かめる

手元の情報が、選んだ趣旨の「前提」を満たすか確かめる。

満たさない場合は、情報を補うか、趣旨を選び直す。

### 手順5: 制約で絞る

index.yaml からその趣旨の候補を引き、
3.3 の制約に合わないものを外す。

読者の制約には、手順2 の末尾の制約（符号化が読み手の慣習にあるか）を含める。

候補が一つも残らない場合は、手順7 の組み合わせ（5.2）に進むか、文章か表に割り当てる（1.4）。
概観と正確な値の両方が必要な場合は、精度を overview として候補を絞り、正確な値は手順7 の組み合わせで担う（5.2）。

### 手順6: 候補を一つに決める

index.yaml の候補は、読み手の認知コスト（1.2 の推論コスト）が低い順に並ぶ（6.4）。
`when` のない先頭の候補が第一候補である。

`when` の条件に当たる候補がある場合は、そちらに切り替える。
複数の候補の `when` に同時に当たる場合は、そのうち手順1の答えと精度を運べる候補の中で、
先に並ぶ（認知コストの低い）候補を選ぶ（adr/0015）。

### 手順7: 組み合わせを検討する

手順6で決めたパターンだけでは残りの問いに答えられない場合、
または規模の制約を超える場合に限り、
5.2 の条件に従って Composition または Narrative を検討する。

### 手順8: 作図する

選んだパターンで、手順1の答えをどう図の形にするかを決めてから描く。

- 答えの主張一つを図の形にする。答えを意図の型（6.3 の一覧）に当てはめ、
  パターン文書の「意図の型と手段」にその型の手段があれば、それを使う。
  なければ「デザインの文法」「作成時のルール」に従って描き、注釈の種類は 6.3 の順で選ぶ。手順9 の記録に「手段なし」と残す（`development.md`「改善」）
- 載せるデータに制約は置かない。主張の文脈になる項目は載せてよい。
  ただし、主張以外の意図（他の項目との比較、順位、因果など）を読み手に誤推論させない表現にする
- 答えの一文をキャプションに書く（1.4）

### 手順9: 伝達ギャップを検証する

実際に伝わる内容は、作ってみるまで分からない。
作成後に次を確かめる。

- 逆読み: 図表（文章を選んだ場合は文章）だけから読み手が引き出す結論を書き出し、
  手順1の答えと照合する。
  可能なら、伝達目標を知らない別のエージェントに読ませて説明させる
  - 答えに届かない（欠落）:
    図表なら添え書きを足すか、1.3 の左側に寄せる。
    文章なら構造化するか、1.3 の右側に寄せる
  - 余計な意味が読める（誤推論）: 配置・矢印・色・強調を直す
- 削除: 図表を消して添え書きだけにしても答えが伝わるなら、図表を削る。
  文章を選んだ場合は、読み手が図のほうが読みやすかったと答えたら、1.3 の右側に寄せる
- 重複: 本文と図表が同じ情報を同じ粒度で繰り返していれば、片方を削る

逆読みの結果は記録に残し、欠落・誤推論は `development.md`「改善」の手順で本書へ反映する。

## 3. 選択の入力

### 3.1 趣旨 (intents)

趣旨は読み手の問いの型であり、図表を見た読み手が答えられるようになる問いで定義する。

データの形の名前（階層、順序など）や、
読んだ後の行為（意思決定など）では定義しない。

同じ情報でも、問いが違えば趣旨は別になる。

例えば月次売上のデータでも、
問いが「どう推移したか」なら時系列変化、
「どの月が多いか」なら大小比較である。

各趣旨は以下の項目で定義する。

| 項目 | 内容 |
| --- | --- |
| ID | 英小文字のkebab-case。frontmatter と index.yaml で使用する |
| 問い | 読み手が答えられるようになる問い |
| 前提 | その問いが成立するために必要な情報構造（3.2 の表記） |
| 境界 | 隣接する趣旨との使い分け |

趣旨ごとの候補パターンと切替条件は index.yaml に定義する。

答えそのもの（意図）は趣旨より細かく、本書には書かない（手順1）。
答えの抽象である意図の型は、パターン文書の「意図の型と手段」で扱う（6.3）。

趣旨はすべて、表現形式ごとの分類文書（6.1）で定義する。

| --- | --- | --- |
| chart | `chart/chart.md` | Visual Vocabulary |

| picture | `picture/picture.md` | 本書独自 |

趣旨は候補パターンの表現形式を縛らない。
例えば工程の第一候補 Gantt chart は、4.1 の分類原則により chart である。

#### 趣旨の追加

趣旨を追加する際は以下に従う。

- 候補パターンが一つもない趣旨は定義しない
- 情報構造・視覚的符号化・カテゴリと同じ名称は、問いに合わせて改名する。
  例: 階層 → 親子関係、包含 → 所属
- 定義したら、`fixtures/fixtures.md` に場面を追加する（7章「検証」）

検討中の趣旨は、定義するまで `adr/` に draft として置く（adr/0001）。

### 3.2 情報構造 (information_structure)

手元の情報の形を、データの形と属性の尺度の二段で表す。

#### データの形 (shape)

| 形 | 意味 |
| --- | --- |
| items | 項目の集合。各項目が属性を持つ |
| matrix | 二種類のキーの組み合わせごとに値を持つ |
| sequence | 項目が一列の前後関係を持つ |
| hierarchy | 項目が親子関係を持つ |
| graph | 項目が任意の関係で結ばれる |
| state-machine | 状態と遷移 |
| spatial | 項目が座標や領域を持つ |
| object | 対象そのもの。画面や写真として取得できる |

sequence・hierarchy・state-machine は graph の特殊形である。

当てはまる中で最も特殊な形を指定する。

趣旨の前提に挙げた形より特殊な形も、その前提を満たす。

object は他の形と組み合わせない。属性の尺度も指定しない。

#### 属性の尺度 (attributes)

| 尺度 | 意味 |
| --- | --- |
| categorical | 順序のない区分 |
| ordinal | 順序はあるが、間隔に意味のない区分 |
| quantitative | 数値 |
| temporal | 時刻・期間 |

項目同士の前後関係は sequence（形）で表し、
ordinal・temporal（属性）と区別する。

やり取りの主体（誰が）は categorical 属性として表す。

#### 表記

前提は `形: 属性 + 属性` と書く。

frontmatter では以下のように書く。

Line Chartなら、
```yaml
information_structure:
  shape: items
  attributes:
    - temporal
    - quantitative
```

Flowchartなら、
```yaml
information_structure:
  shape: graph
  attributes: []
```

Sequence Diagramなら、
```yaml
information_structure:
  shape: sequence
  attributes:
    - categorical
```
である。

### 3.3 制約

| 制約 | 問い | パターン側の記述 |
| --- | --- | --- |
| 規模 | 項目数・系列数・階層の深さは、パターンが読める範囲に収まるか | `scale` |
| 精度 | 傾向や構造が分かればよいか、個々の値を正確に読ませるか | `precision` |
| 読者 | 読み手はその記法の読み方を知っているか | `complexity` |
| 出力媒体 | その媒体で作成・表示できるか。実物の素材が必要か | `avoid_when` |

#### 精度 (precision)

| 値 | 意味 |
| --- | --- |
| overview | 傾向・構造・関係が分かればよい |
| exact | 個々の値や条件を正確に読ませる |

#### 読者 (complexity)

読み手に要求する記法の知識を示す。

| 値 | 意味 | 例 |
| --- | --- | --- |
| low | 説明なしで読める | Bar Chart, Comparison Table |
| medium | 一般的な記法の知識が必要 | Flowchart |
| high | 専門的な記法の知識が必要 | ER Diagram, Sequence Diagram |

読み手がその記法を知らない場合は、
凡例を付けるか、complexity の低いパターンに切り替える。

## 4. パターンの記述属性

以下は選択の入力ではない。

選ばれたパターンがどのような表現であるかを説明する属性である。

### 4.1 表現形式 (families)

| 表現形式 | 定義 | 例 |
| --- | --- | --- |
| chart | データ値を位置・長さ・面積・色などの視覚属性へ符号化する | Bar Chart, Line Chart |
| diagram | 関係・構造・処理・状態などを空間配置や接続で表現する | Flowchart, ER Diagram |
| picture | 対象そのものの外観・空間・具体例を示す | Screenshot, Photo |
| table | 行・列という構造を用いて情報の検索・照合・比較を行う | Comparison Table |

表現形式は選択の起点にしない。
カタログの整理とパターンの説明に使用する。

#### 分類原則

表現形式は見た目ではなく、主要な情報伝達手段によって分類する。

目的による違いは趣旨（3.1）で扱い、表現形式の判定には使用しない。

例えばHeatmapは表に似た外観を持つが、
色によって値を符号化しているためChartに分類する。

セルに数値を併記していても、
数値を消して成立するのであればChartである。

セルの内容を読まなければ成立しないものはTableに分類する。

### 4.2 視覚的符号化 (visual_encoding)

| 符号化 | 意味 |
|---|---|
| position | 位置 |
| length | 長さ |
| size | 大きさ |
| area | 面積 |
| angle | 角度 |
| color | 色 |
| shape | 形 |
| connection | 接続 |
| containment | 包含 |
| proximity | 近接 |
| alignment | 整列 |
| texture | 模様 |

符号化は「どの情報を、どの視覚属性に対応づけるか」を記述する。

ノードや棒などの図形そのものは含めない。

Bar Chartなら、
```
category → position
value → length
```

Tree Diagramなら、
```
parent-child relationship → connection
depth → position
```
である。

量を正確に比べさせる場合は position と length を優先する。

angle・area・color は差を読み取りにくいため、
精度が overview の場合に限って使用する。

### 4.3 テキスト依存度 (text_dependency)

図表の主要な意味を理解するために、
文字情報を読む必要がある程度を示す。

#### Low

文字を読まなくても主要な傾向・構造・関係を知覚できる。

例:
Bar Chart
Scatter Plot
Heatmap

#### Medium

ラベルなどの文字情報は必要だが、
主要な構造や関係は視覚的に把握できる。

例:
Flowchart
Architecture Diagram

#### High

個々の文字情報を読まなければ主要な情報を取得できない。

例:
Comparison Table
Decision Table

---

テキスト依存度が高いこと自体は品質上の問題ではない。

図表の目的とテキスト依存度が一致しているかを、
精度の制約（3.3）との対応で評価する。

| 精度 | 期待されるテキスト依存度 |
| --- | --- |
| overview | Low または Medium |
| exact | High まで許容する |

精度が overview であるのに High のパターンを選んでいる場合は、
選択を見直す。

### 4.4 抽象度 (abstraction)

| 抽象度 | 意味 | 例 |
| --- | --- | --- |
| concrete | 実物そのもの、またはそれに近い表現 | Screenshot, Photo |
| schematic | 不要な情報を除き、重要な構造だけ残した表現 | Wireframe, Floor Plan |
| abstract | 対象を概念・関係・数値などに還元した表現 | Bar Chart, Flowchart |

抽象度は表現形式だけでは決まらない。

同じ画面を示す場合でも、
実物と照合させるなら concrete（Screenshot）、
レイアウトの構造を理解させるなら schematic（Wireframe）を選ぶ。

## 5. パターン階層と組み合わせ

### 5.1 パターン階層 (layer)

図表パターンを以下の３階層に分類する。

#### Primitive

単一の視覚表現。

例:
Bar Chart
Flowchart
Sequence Diagram
Comparison Table
Screenshot

#### Composition

複数のPrimitive（同じPrimitiveの反復を含む）を、
一つの情報表現として組み合わせる方法。

例:
Overview + Detail
Visual + Exact Values
Before + After
Small Multiples

#### Narrative

複数の図表を文書内で順序付け、
段階的に理解させるための構成。

例:

System Context
→ Architecture
→ Component Detail
→ Sequence

---

一つの図番号・キャプションのもとで同時に参照される場合はCompositionとする。

それぞれが独立した図として成立し、
文書の進行に沿って段階的に提示する場合はNarrativeとする。

### 5.2 組み合わせを使う条件

以下のいずれにも当たらない場合は、Primitive 一つで表現する。

Composition:

| 条件 | 例 |
| --- | --- |
| 一つの対象について、概観と正確な値の両方が必要 | Visual + Exact Values |
| 規模がPrimitiveの読める範囲を超える | Overview + Detail, Small Multiples |
| 同じ対象の二つの状態を見比べさせる | Before + After |

Narrative:

- 全体を一つの図に収めると規模の制約を超え、
  抽象度の段階を踏んで説明できる
- 前の図を理解していなければ、次の図が読めない

### 5.3 組み合わせ関係 (relation)

| 関係 | 意味 |
|---|---|
| complementary | 異なる情報を補完する |
| comparative | 並べて差を見る |
| contextual | 一方が他方の文脈になる |
| hierarchical | 全体と部分 |
| sequential | 前後関係を持つ |
| explanatory | 一方が他方を説明する |
| redundant | 同じ情報を重複して表現する |

redundantは、同じ問いに同じ精度で答える重複を指す。

同じデータを使用していても、
答える問いや精度が異なる場合はredundantではない。

例えば Visual + Exact Values は、
チャートが概観を、表が正確な値を担うため complementary である。

redundantな組み合わせは原則として避ける。

ただしアクセシビリティや、
重要情報を複数表現で強調する明確な理由がある場合を除く。

## 6. パターン定義スキーマ

### 6.1 ファイル配置

| 階層 | 配置 |
| --- | --- |
| primitive | `<family>/<id>.md` |
| composition | `composition/<id>.md` |
| narrative | `narrative/<id>.md` |

表現形式ごとの分類文書は `<family>/<family>.md` に置く（例: `chart/chart.md`）。
その表現形式に属する趣旨の定義（3.1）と、候補の決め方を書く。
パターンではないので、index.yaml には登録しない。

### 6.2 frontmatter

| キー | 必須 | 値 | 定義 |
| --- | --- | --- | --- |
| `id` | ○ | Pattern ID。ファイル名と一致させる | 8章 |
| `name` | ○ | 表示名 | 8章 |
| `aliases` | | 同義語のリスト | 8章 |
| `layer` | ○ | `primitive` / `composition` / `narrative` | 5.1 |
| `family` | primitive | `chart` / `diagram` / `picture` / `table` | 4.1 |
| `relation` | composition, narrative | 組み合わせ関係 | 5.3 |
| `primary_intent` | ○ | 属する趣旨の ID を一つ | 3.1 |
| `secondary_intents` | | 候補に挙がる他の趣旨の ID のリスト。index.yaml でそのパターンが候補に挙がる趣旨から `primary_intent` を除いたものと一致させる | 3.1、6.4 |
| `information_structure` | primitive | `shape` を一つ、`attributes` をリストで指定する | 3.2 |
| `scale` | | 規模の軸と、読める範囲 | 3.3 |
| `precision` | ○ | `overview` / `exact` | 3.3 |
| `complexity` | ○ | `low` / `medium` / `high` | 3.3 |
| `visual_encoding` | primitive | 情報と符号化の対応 | 4.2 |
| `text_dependency` | primitive | `low` / `medium` / `high` | 4.3 |
| `abstraction` | primitive | `concrete` / `schematic` / `abstract` | 4.4 |
| `best_for` | | 適する場面 | |
| `avoid_when` | | 避ける場面。出力媒体の制限もここに書く | |
| `alternatives` | | 代替となるパターンの ID | |

定義済みでない趣旨（`adr/` の draft を含む）は `primary_intent`・`secondary_intents` に指定しない。

### 6.3 本文

本文は以下の節で構成する。

- 定義
- 目的
- どういうときに利用するか
- どういうときに利用してはいけないか
- 入力の構造
- デザインの文法
- 作成時のルール
- 意図の型と手段
- やってはいけないこと
- 利用例
- NGパターン

「意図の型と手段」は、答えの型ごとに、そのパターンの中でどの手段で答えを運ぶかを表にする。
手段は、注釈（「注釈の種類」の四種類）と、注釈でない手段（軸の範囲・基準線・並び順・配置）からなる。
手段の行には、使う注釈の種類の名前を書く。

| 意図の型 | 手段 |
| --- | --- |

型の名前は次の一覧にあるものを使う。
型は先に作らず、逆読みの失敗から一般化したときに加える（`development.md`「改善」、adr/0007、adr/0012）。
行がない状態でもよい。逆読みの記録（`fixtures/gyakuyomi.md`）は本文から引かない（adr/0012）。

#### 意図の型の一覧

答えの抽象である意図の型。パターン文書の「意図の型と手段」はこの名前を使う。

| 意図の型 | 意味 |
| --- | --- |
| 一項目の変化 | 多くの項目の中で、一つの項目の値が時点の間でどう変わったか。他の項目は文脈で、比較は主題でない |
| 入れ替わり | 二つ以上の項目のどちらが上かが、時点や区分（年代など）で入れ替わる。または上にある項目との差が時点の間で変わる |
| 段階の性質 | 多くの段階からなる手順や経路の中で、一つの段階が持つ性質（自動か人手か、同期か非同期かなど）が主張。他の段階は経路の文脈で、順序そのものは主題でない |
| 受け渡しでの損失 | 経路を進むものの一部が、受け渡しのたびに失われることが主張。残る量や失われる量の値は主題でない |
| 受け渡しでの変質 | 経路を進むものが、受け渡しのたびに一部を失い、別のものが加わって、中身が元とは別のものへ変わっていくことが主張。量より中身の変化が主題で、値は主題でない |

パターン同士の使い分けは本文に書かない。

同じ趣旨の候補間の切替条件は index.yaml に、
趣旨をまたぐ使い分けは 3.1 の境界に定義する。

#### 注釈の種類

注釈は、主張の対象に読み手の注意を向けて答えを運ぶ操作で、次の四種類がある（adr/0017）。

| 種類 | 操作 | 共通の制約 |
| --- | --- | --- |
| 言語的 | 値・差・名前・一文を図の中に書く | 読ませたい箇所のそばに置き、凡例との往復をさせない |
| 幾何的 | 太さ・大きさ・位置・向きなど、図形の操作で対象を際立たせる | そのパターンの符号化（4.2）が読ませる長さ・面積・角度・位置を変えない。使える操作と使えない操作はパターンごとに異なる |
| 色彩的 | 色相と明度で対象を際立たせる | 色相は、一つの対象を際立たせる（強調の色相は図に一つ、他は無彩色か抑えた色）、二つの対象を補色で対比させる、似た色相で群を束ねる、のいずれかに使う。明度は順序や程度を表し、強調には最も濃い段を当てる。答えが述べる対象（すべての項目に及ぶ主張の全項目、前後や差の相手になる項目）は無彩色にしない。無彩色の項目は答えの対象外と読まれる。強調の差は同じ色相の明度で付ける |
| 意匠的 | 星印・注目の矢印・枠など、上の三つに当たらないデザインの工夫 | 符号化に使う記号（diagram の矢印は接続）と見分けがつくこと |

パターンごとの制約は、使える操作を「作成時のルール」に、使えない操作を「やってはいけないこと」に書く。

種類は次の順で選ぶ（手順8）。

1. そのパターンの制約で使える種類に絞る
2. 読み手の慣習にある種類を先にする（手順2 の末尾の制約）。言語的と色彩的は慣習が広く、幾何的と意匠的は図法によっては学習を要する
3. 意図しない意味を足さない種類を選ぶ（手順2 の末尾の制約）。星印は評価や順位、矢印は流れや因果、枠は所属を読ませうる
4. 一つの対象に重ねる種類は二つまでを目安にする

### 6.4 index.yaml

```yaml
intents:
  <intent-id>:
    candidates:
      - pattern: <pattern-id>
      - pattern: <pattern-id>
        when: <切替条件>

patterns:
  - id: <pattern-id>
    layer: <layer>
    family: <family>
    path: <ファイルパス>
  - id: <pattern-id>
    name: <表示名>
    layer: <layer>
    family: <family>
    status: planned
```

- `intents` のキーは 3.1 で定義済みの趣旨の ID とする
- `candidates` は読み手の認知コストが低い順に並べる。先頭が第一候補であり、`when` を書かない。
  認知コストは、符号化が読み手の慣習にあるか（手順2 の末尾の制約）、符号化の数（4.2）、テキスト依存度（4.3）で見積もり、
  候補を加えるときに順序を決めておく。手順6 は、複数の `when` に当たるときにこの順序で選ぶ
- 二番目以降の候補には、切り替える条件を `when` に書く
- `candidates` に指定するパターンは、すべて `patterns` に登録する
- ファイルが未作成のパターンは、`path` の代わりに `status: planned` を指定する。
  frontmatter がないため、表示名を `name` に書く
- frontmatter を正とし、index.yaml はそれと一致させる

## 7. 分類ルール

### 選択条件

選択条件とは、primary intent（属する趣旨）・情報構造・制約（3章）の組を指す。

### 複数Intent

一つのパターンが複数の趣旨の候補に挙がることを許可する。

ただし属する趣旨（primary intent）を一つ指定する。
候補に挙がる他の趣旨は `secondary_intents` に書き、index.yaml と一致させる（6.2）。

### Family

一つのPrimitiveは原則として一つのFamilyに所属する。

判定は 4.1 の分類原則に従う。

### Composition

Primitiveを組み合わせた結果として新しい役割が生じる場合、
Composition Patternとして定義する。

単に複数の図を並べただけの場合は、
新しいComposition Patternとはみなさない。

### 新規パターン

既存パターンとの差が外観だけの場合、
原則として新規パターンを作成しない。

選択条件、または視覚的符号化に
意味のある違いが存在する場合に新規パターンとする。

### 検討中の内容

決定していない内容は、taxonomy.md・`<family>/<family>.md`・index.yaml・`development.md` に書かない。

`adr/` に draft として置き、採用したときに本体へ反映する（`adr/README.md`）。

### 検証

趣旨を定義・変更した場合、または index.yaml の候補を変更した場合は、
`fixtures/fixtures.md` のすべての場面を選択手順に通し、
結論が一つに決まり、変更前と意図せず変わっていないことを確かめる。

結論が変わる場合は、変更の理由とともに場面の結論を更新する。

## 8. 命名規則

Pattern IDは英小文字のkebab-caseとする。

趣旨の ID も同じ規則に従う。

例:

```
bar-chart
sequence-diagram
overview-detail
visual-exact-values
```

表示名には一般的に認知された名称を使用する。

独自名称を使用する場合は、
既存パターンとの違いを本文の「定義」内で明示する。

同義語はaliasesとして定義し、
別パターンを作成しない。

例:

```yaml
id: scatter-plot
aliases:
  - scatter-chart
  - scatter-graph
```
