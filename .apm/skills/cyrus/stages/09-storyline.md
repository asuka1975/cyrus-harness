# ステージ9: 話の流れを決める（Storyline Design）

フェーズ: 組み立て 3/5　成果物: `09-storyline.json`　承認: 必要

## ねらい

各節で読者が持ち帰る**1文のメッセージ**を決め、それらを順に読むだけで文書全体の話が通るようにします。
このメッセージの列は、ステージ12の拾い読みテストで「伝わったかどうか」を判定する基準になります。

## 進め方

1. 話の型（pattern）を選ぶ。
   - PREP: 結論 → 理由 → 具体例 → 結論（提案・意見）
   - SCQA: 状況 → 問題 → 問い → 答え（問題解決の提案）
   - 時系列: 手順書・経緯の報告
   - 全体 → 部分: 解説
2. 各節のメッセージを書く。
   - 1文で、80字以内を目安にする（120字を超えるとエラー）。
   - 見出しの言い換えではなく、**主張**にする（「現状について」ではなく「いまの検索では、当日の記事が翌日まで見つからない」）。
   - その節に割り当てた主張の確からしさ（07-logic/report.json の hedge）に合った強さで書く。
3. 各節に、前の節からのつなぎ（bridge）を書く。読者が「なぜ次にこの話が来るのか」を感じられる一言にする（例: 「では、なぜ遅いのか」）。
4. メッセージだけを上から順に読み、次を確かめる。
   - 話が飛んでいないか（つなぎが不自然な箇所は、節の順序か内容に問題がある）
   - 同じことを2回言っていないか
   - 読者の疑問にすべて答えているか
5. 全体を1文で表す summary を書く。01-intent.md の「伝えたいこと」と食い違っていれば、どちらが正しいかユーザーに確かめる。
6. 節の順序や数を変えたくなったら、08-structure.json も直して整合させる（`cyrus check` が順序の違いを検出する）。

## ユーザーへの承認

ステージ8の骨組みとこのストーリーをまとめて見せます。見せ方は次のようにします。

```
全体: （summary）
1. 要約 — （メッセージ）
2. いま何が困っているか — （メッセージ）
…
```

「この流れで書き始めてよいですか。入れ替えたい順番や、足りない話はありますか」と聞きます。ここで承認されれば、執筆後の大きな手戻りを防げます。
