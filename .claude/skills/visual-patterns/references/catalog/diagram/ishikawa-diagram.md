# 特性要因図

## 定義

一つの結果（特性）を右端に置き、そこへ向かう背骨から分類ごとの大骨を伸ばし、各分類の原因を小骨として並べた図である。魚の骨の形から魚骨図とも呼ぶ。原因はさらに細かい原因に枝分かれしてよい。

## 目的

読み手が「この結果の原因はどの分類にあり、各分類にどんな原因が挙がるか」に答えられるようにする。

## どういうときに利用するか

- 品質問題や障害の原因候補を、人・設備・方法・材料などの分類で網羅したい
- 原因の候補が多く、分類せずに列挙すると偏りや漏れが見えない
- 原因の洗い出しの結果を、調査の範囲として共有したい

## どういうときに利用してはいけないか

- 原因から結果への連鎖の順序が主題である。骨は分類を示し、順序を示さない
- 原因の組み合わせ条件（AND・OR）を正確に読ませたい
- 結果が複数あり、一つの背骨に収まらない

## 入力の構造

hierarchy: categorical。根が結果、子が分類、孫以下が原因。原因は分類の属性を持つ。

```yaml
effect: 夜間バッチの遅延
causes:
  - {category: 設備, items: [ディスク I/O の競合, メモリ不足]}
  - {category: 方法, items: [全件再計算]}
```

## デザインの文法

- 結果を右端の枠に置き、背骨を左から右へ引いて結果に向ける
- 分類ごとに大骨を背骨の上下に交互に伸ばし、分類名を先端に書く
- 原因は大骨に沿って小骨として並べ、細かい原因はさらに枝にする
- 分類は 4〜8 にし、慣例の分類（4M など）を使う場合はその名前で統一する

## 作成時のルール

- 結果は一つに絞り、測れる形で書く（「遅い」ではなく「処理が 2 時間を超える」）
- 原因は短い名詞句にし、推測の原因と確認済みの原因を色で区別する
- 調査で特定した主要因を強調し、図の結論として本文に一文で書く

## やってはいけないこと

- 骨の順序に時間や重要度の意味を持たせる
- 一つの原因を複数の分類に重複して書く
- 対策や担当者を原因として骨に書く

## 利用例

- 製造工程の不良率の原因分析。人・設備・方法・材料の分類で原因を洗い出す
- 障害のふりかえり。再発防止の検討範囲として原因候補を分類して示す

## NGパターン

- 確定した原因一つだけを骨に書く。分類して洗い出す意味がなく、文章で足りる
- 小骨に対策を混ぜる。原因と対策の区別が消え、何が結果を引き起こしたのか読めなくなる
