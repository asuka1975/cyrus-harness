# データフロー図

## 定義

処理・データストア・外部実体を記号で区別し、その間を移動するデータを矢印で結んだ図である。矢印にデータの名前を書き、何がどこへ渡るかを示す。処理の順序や条件は描かず、データの受け渡しだけを描く。

## 目的

読み手が「この処理は何を必要とし、このデータを変えると何に影響するか」に答えられるようにする。

## どういうときに利用するか

- バッチやサービスがどのデータストアを読み書きするかを示したい
- データ項目の変更が及ぶ範囲（影響分析）を辿らせたい
- 外部システムとの受け渡しを、システムの境界とともに示したい

## どういうときに利用してはいけないか

- 処理の実行順や条件分岐が主題である。この図は順序を示さない
- 移動したデータの量や件数を比べさせたい
- 読み手が記号を知らず、凡例を付けても処理と保存先を取り違える（手順2 の末尾の制約）

## 入力の構造

graph: categorical。ノードが処理・データストア・外部実体の種別を持ち、辺がデータの名前を持ち、送る側から受ける側へ向く。
依存の趣旨の辺（必要とする側 → 必要とされる側）から描くときは、向きを逆にする。集計バッチが売上DBを必要とする依存は、データフローでは `売上DB → 集計バッチ` になる。

```yaml
nodes:
  - {id: 集計バッチ, type: process}
  - {id: 売上DB, type: store}
edges: [{from: 売上DB, to: 集計バッチ, data: 日次売上}]
```

## デザインの文法

- 処理は円か角丸の長方形、データストアは開いた長方形、外部実体は長方形で描き、一つの記法に統一する
- 矢印はデータの移動の向きにし、矢印にデータの名前を書く
- 外部実体を図の縁に、処理を中央に、データストアを処理の近くに置く
- システムの境界を枠で囲み、枠の内外で担当範囲を区別する

## 作成時のルール

- 記法（Yourdon、Gane-Sarson など）を明記し、凡例を付ける
- 処理の粒度を一つの図でそろえ、詳細は階層化した別の図に分ける
- 影響を辿らせたい経路を強調し、結論を本文に一文で書く

## やってはいけないこと

- 矢印にデータの名前を書かず、何が渡るか分からない線にする
- 処理の順序や条件分岐を矢印で表す
- 処理から処理へ直接渡す矢印と、データストア経由の受け渡しを混同する

## 利用例

- 夜間バッチの読み書き。どのデータストアを読み、どこへ書き、何が変更の影響を受けるかを示す
- 外部システムとの連携仕様。受け取るデータと返すデータを境界とともに示す

## NGパターン

- 処理を矢印で順に結んだ図。順序の図になり、何がどのデータを必要とするか読めない
- すべての処理を一枚に詰め込む。矢印が交差し、影響の範囲を辿れない
