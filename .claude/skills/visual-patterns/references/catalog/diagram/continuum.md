# 両極スケール

## 定義

対立する二つの極を線の両端に置き、対象をその線上の位置で示した図である。位置は測定値ではなく評価で決める。線の途中に段階の目印を置くことがある。

## 目的

読み手が「この対象は二つの極のどちらにどれだけ寄っているか、他と比べてどうか」に答えられるようにする。

## どういうときに利用するか

- 設計方針や製品を「柔軟性 ⇄ 単純さ」のような一つの観点で位置づけたい
- 対象が複数あり、相対的な位置を一列で比べさせたい
- 両極が対立する価値で、どちらかが正解ではないことを示したい

## どういうときに利用してはいけないか

- 観点が二つ以上あり、一本の線では位置を決められない
- 位置が測定値で、正確に読ませたい。線上の位置は評価の目安にすぎない
- 両極が対立せず、量の大小しかない

## 入力の構造

items: categorical + ordinal。各対象が、両極の間の段階を一つ持つ。

```yaml
poles: {left: 一貫性, right: 可用性}
items:
  - {name: システムA, position: やや左}
  - {name: システムB, position: 右}
```

## デザインの文法

- 線を横に引き、両端に極の名前を書く
- 対象は線上の点か短い縦線で示し、名前を添える
- 段階の目印（中央など）を薄く置き、位置の読み方をそろえる
- 対象をグループで分ける場合は色を使い、凡例を付ける

## 作成時のルール

- 両極が本当に対立する概念かを確かめ、一方向の大小ならこの図を使わない
- 位置を決めた評価の基準をキャプションか本文に書く
- 読み取ってほしい結論（どの対象がどちら寄りか）を本文に一文で書く

## やってはいけないこと

- 線に目盛りを付け、評価の位置を測定値のように見せる
- 一方の極を良、他方を悪として色付けする
- 対象を線上に重ねて置き、どれがどこか分からなくする

## 利用例

- データベース製品の方針。一貫性と可用性の間でどこを重視するかを位置づける
- 開発プロセスの選択。計画重視と適応重視の間でチームの現状と目標を示す

## NGパターン

- 両極を「低い ⇄ 高い」にする。対立する価値ではなく量の大小であり、評価の線に置く意味がない
- 10 を超える対象を一本の線に置く。名前が重なり、相対的な位置が読めない
