# visual-patterns: 図表を「読み取らせたいこと」から選び、描く

図表は、読み手に何を読み取らせたいかから選びます。表現形式から選び始めません。
文章も図表も読み手にコストを課します。文章は量を読んで構造を組み立て直す処理コスト、図表は符号化を解読して省かれた部分を補う推論コストです。
文章で理解に失敗した読み手は失敗を自覚しますが、図表を誤読した読み手は自覚しにくい。だから図表には文章（キャプション）を添え、誤読の余地をパターンの選択と注釈で狭めます。

カタログの本体は `references/catalog/taxonomy.md` です。この SKILL.md は、その選択手順（2章）を実行するための短い手順書です。迷ったら本体を読みます。

## 入力

呼び出し元（ハーネス、または自分で書き出したメモ）から受け取ります。欠けている項目は、推定で補わず、呼び出し元に聞きます。

- **答え**: この箇所で読み手に持ち帰ってほしい主張。一文。参照用の情報なら、何を探し当てればよいか
- **根拠**: 作者がその答えを支えるために同じ文書に示したもの（値の集まり、項目と属性、段階・主体・部分とその関係、条件と結果、外観）。**数を添える**（例: 3 区分 × 2 時点の表、主体 2 と段階 4）
- **読み手**: 知識の程度、その記法（フローチャート、シーケンス図など）を知っているか
- **精度**: 正確な値が要るか（exact）、大小・傾向・形がわかれば足りるか（overview）
- **読み方**: 通読して理解するか（through）、必要な箇所を探して参照するか（lookup）
- **媒体**: Markdown（GitHub・Wiki）、PDF、スライドなど。Mermaid をそのまま表示できるか、画像を置けるか

## 手順

出力は「figure spec」（下の形式）です。手順1〜7 で spec を書き、`scripts/vp_figure.py check` で確かめ、手順8 で描き、手順9 で検証します。

### 1. 伝達目標を書く（問い・答え・根拠・精度・読み方）

答えが一文で書けなければ、表現を選ぶ前に内容を整理します。主張が複数あるなら、主となる一つを答えにし、残りは別の図かキャプションに回します。述語が二つある文（「〜し、〜」「〜および〜」）は主張が二つです。
根拠は一文にまとめません。手順2 は根拠の数と形を見ます。

### 2. 根拠の形で、文章か図表かを決める

根拠を次の表に当てはめます。当たる行があれば図表を候補にし、どの行にも当たらなければ**文章（箇条書きを含む）で書きます**。答えが一文で言えること、答えが条件・理由・否定を含むことは、文章を選ぶ理由になりません（条件や理由は添え書きが担います）。

| 根拠の形（`evidence.form`） | 図表にする目安 | 選べる趣旨のカテゴリ |
| --- | --- | --- |
| 量 `quantity` | 答えが述べる対象の値が 5 つ以上（`values`）。または 2 つ以上の区分を 2 つ以上の時点・条件で比べる増減・差が答えで、差の大きさが精度に含まれる（`groups` ≥ 2、`periods` ≥ 2、`difference_matters`） | 比較・変化・構成・分布・地理・相関・流量 |
| 項目×属性 `items-attributes` | 対象 2 つ以上 × 観点 3 つ以上、または対象 5 つ以上 × 観点 2 つ以上（`items`、`categories`） | 属性比較・位置づけ・値検索 |
| 段階・主体・部分 `parts-relations` | 主体・部分が 2 つ以上あり、段階と合わせて 4 つ以上（`actors`、`steps`）。または数によらず分岐・合流・循環・多対多・入れ子を含む（`features`）。または出来事の前後関係が答えで期限が相対で決まる（`relative-timing`）。または主体から主体へ渡るたびに減る・変わることが答え（`loss-per-handoff`・`change-per-handoff`） | プロセス・構造・関係・経緯 |
| 条件と結果 `conditions` | 条件が 2 つ以上あり、どの条件に当たるかで結果が分かれる（`conditions`） | 条件判定 |
| 外観 `appearance` | 形状や見た目が答えで、言葉では一意に特定できない | 外観 |

文章にするのは、値が 4 つ以下の比較や増減、一つの定義・一つの理由・条件がすべて揃って結果が一つに決まる規則、主体が一つで分岐のない段階（番号付きリスト）、3 つ以下の項目の列挙です。
迷ったら根拠を文章で書き出します。同じ文型の文が 3 つ以上並ぶ、または読み手が前の文に戻って照合し直すなら図表にします。

文章を選んだら、手順3〜8 を飛ばして手順9 に進みます。

### 3〜4. 趣旨を決め、情報構造を確かめる

趣旨は読み手の問いの型です（例: 「どれが大きいか」→ 大小比較 `magnitude-comparison`、「どの条件でどう分かれるか」→ 分岐 `branching`）。一覧は `scripts/vp_figure.py intents` で出ます。手順2 で当たった行のカテゴリの中から一つ選びます。
趣旨の定義（問い・前提・境界）は、表現形式ごとの分類文書にあります: `references/catalog/chart/chart.md`、`diagram/diagram.md`、`table/table.md`、`picture/picture.md`。隣り合う趣旨の使い分けは「境界」を読みます。
手元の情報が、その趣旨の「前提」（情報構造。`items: temporal + quantitative` など）を満たすか確かめます。満たさなければ、情報を補うか趣旨を選び直します。

### 5〜6. 候補を制約で絞り、一つに決める

```bash
python3 <このスキル>/scripts/vp_figure.py candidates <趣旨の ID>
```

候補は読み手の認知コストが低い順に並び、**先頭が第一候補**です。2 番目以降は、その `when` の条件に当たるときだけ切り替えます。複数の `when` に当たるなら、答えと精度を運べる候補のうち先に並ぶものを選びます。
規模（項目数・系列数）、精度、読み手の記法の知識、出力媒体（Mermaid で描けるか、画像を置けるか）に合わない候補は外します。候補が一つも残らなければ、組み合わせ（手順7）か、表か文章にします。
第一候補以外を選んだら、第一候補を退けた理由を `rejected` に書きます。

### 7. 組み合わせ

一つのパターンで残りの問いに答えられない、または規模の制約を超えるときだけ、図を分けます（一つの図番号に複数のパターンを入れる Composition は、カタログでまだ定義されていません）。分けた図にはそれぞれ spec を書きます。

### 8. 作図する

描く前に、答えをどう図の形にするかを決めます（`drawing`）。

1. 答えを「意図の型」（taxonomy.md 6.3 の一覧。`vp_figure.py check` が知っている名前だけ）に当てはめる。パターン文書の「意図の型と手段」にその型の手段があれば、それを使う。なければ型は空にし、「デザインの文法」「作成時のルール」に従う
2. 「意図の型と手段」に手段がないとき（手段が注釈の種類を言わないときも）は、注釈の種類を 6.3 の順で絞る: そのパターンの制約で使える種類に絞る → 読み手の慣習にある種類を先にする（言語的・色彩的は慣習が広く、幾何的・意匠的は図法によっては学習を要する）→ 意図しない意味を足さない種類を選ぶ（星印は評価、矢印は流れ、枠は所属を読ませうる）→ 一つの対象に重ねるのは二つまでを目安にする。色彩的は、強調の色相は図に一つ、他は無彩色か抑えた色。**答えが述べる対象（差や前後の相手になる項目も）は無彩色にしない**
3. 主張の文脈になる項目は載せてよい。ただし主張以外の意図（他の項目との比較、順位、因果）を誤推論させない
4. **答えの一文を、そのままキャプションに書く**（「図1: 変更は承認を経てから main に入る。」）。条件・例外・理由は添え書き（本文）が言う。本文と図表に同じ情報を同じ粒度で書かない
5. パターン文書の「やってはいけないこと」「NG パターン」を読んでから描く: `vp_figure.py show <パターンの ID>`

描き方は `references/render.md` にあります。diagram 系は Mermaid で本文に埋め、chart 系は Vega-Lite の仕様（JSON）を書いて `vp_figure.py render` で PNG にします。表は Markdown の表です。

### 9. 伝達ギャップを検証する（逆読み）

実際に伝わる内容は、作ってみるまでわかりません。図表（キャプションも本文も見せない）だけから、伝達目標を知らない別の読み手が引き出す結論を書き出させ、答えと照らします。

- 答えに届かない（欠落）: 添え書きを足すか、文章に寄せる
- 余計な意味が読める（誤推論）: 配置・矢印・色・強調を直す
- 削除の問い: 図表を消して添え書きだけでも答えが伝わるなら、図表を削る。読み手が「文章のほうが読みやすかった」と答えたら、その理由を見る
- 重複: 本文と図表が同じ情報を同じ粒度で繰り返していれば、片方を削る

読み手には、答え・キャプション・本文・趣旨・どの規則の検証かを知らせません。カタログの評価では案内に出典とパターン名だけを書きますが、このスキルの読み手は LLM で、パターン名が主張の形を先に知らせることになるので、出典とパターン名も渡しません。読み方が参照（lookup）の図表にだけ、問いを先に示します。選んだ者・描いた者・判定する者は読み手になりません。判定（一致／部分一致／不一致／誤推論）は、読み手でも作図者でもない判定者が行い、図に描いた要素（項目と数、軸と凡例、接続とラベル）を図のソースで確かめてから判定します。

## figure spec の形式

```json
{
  "question": "読み手がこの箇所で答えを得たい問い",
  "answer": "読み手に持ち帰ってほしい主張。一文（80 字以内が目安）",
  "evidence": {
    "form": "quantity | items-attributes | parts-relations | conditions | appearance",
    "description": "根拠を、数を添えて（例: 3 区分 × 2 時点の表）",
    "counts": {"values": 6, "groups": 3, "periods": 2, "series": 3},
    "features": ["branching"],
    "difference_matters": true
  },
  "precision": "overview | exact",
  "reading": "through | lookup",
  "intent": "time-series-change",
  "pattern": "slope-chart",
  "rejected": [{"pattern": "line-chart", "reason": "二時点に絞って比べるので slope-chart の when に当たる"}],
  "intent_type": "入れ替わり",
  "drawing": "各時点で A と B の差を注釈し、入れ替わる時点に印と一文を置く。終点で上にある B の線を太くし、他は細く。線の色は上昇・下降・横ばいで分ける（A は答えの相手なので無彩色にしない）",
  "render": "mermaid | vega-lite | markdown-table | image"
}
```

- `counts` の軸: `values`（答えが述べる値の数）、`groups`（区分）、`periods`（時点・条件）、`series`、`items`（対象）、`categories`（観点）、`actors`（主体・部分）、`steps`（段階）、`conditions`、`levels`、`nodes`、`edges`、`regions`、`cells`、`points`。パターンの規模の制約（`scale`）と同じ名前で書くと、`check` が照合します
- `features`: `branching`、`merging`、`cycle`、`many-to-many`、`nesting`、`relative-timing`、`loss-per-handoff`、`change-per-handoff`
- `evidence.below_threshold_reason`（任意）: 手順2 の目安に満たない根拠を、根拠を文章で書き出して確かめた上で図表にするときの理由。`repeated-pattern`（同じ文型の文が 3 つ以上並ぶ）か `cross-reference`（読み手が前の文に戻って照合し直す）。これがあると `VP020` は警告になる
- `intent_type` は任意。一覧にない型は書きません（型は、逆読みの失敗からカタログの側で増やすものです）
- `rejected` は、第一候補以外を選んだときに書きます

検査:

```bash
python3 <このスキル>/scripts/vp_figure.py check spec.json [--kind figure|table] [--reader-level novice|intermediate|expert]
```

`VP020` が出たら、手順2 の目安では文章です。図表にしたいなら根拠の数を見直します（数を水増ししない）。`VP031` は根拠の形と趣旨の不一致、`VP041` は候補にないパターン、`VP053` は精度 exact に対して概観のパターン、`VP071` は描く手段がないパターン、`VP074` は `render` がパターンの描き方と違う（`render` を直す）、`VP073` はその描き方の注意（警告）です。

## 守ること

- カタログの本体（`references/catalog/`）を書き換えない。趣旨・候補・意図の型は、カタログの側で逆読みの失敗から育てる。ここで増やさない
- 定義のない趣旨（差分・状態変化・並列・外れ値・密度・位置・距離・配置）やパターン（`status: planned`、Petri net、Process event chain）は使わない。経路は `index.json` の 27 の趣旨だけ
- 手順2 の目安の数（値 5 つ以上、対象 2 × 観点 3 など）を、その場の都合で動かさない。目安を改めるのは、カタログの側で逆読みの結果を積んでから
- 図表を増やすこと自体を目的にしない。手順2 で文章になった箇所は文章で書く。図表は根拠の形を見せ、文章が答えを言う
- 逆読みの読み手に、答え・キャプション・本文・趣旨・手段を渡さない（このスキルでは出典・パターン名も渡さない）。読み方が参照の図表にだけ、問いを渡す。削除の問いの答えは、一致の判定に混ぜない
- 装飾のためだけの図は対象外。模式図（wireframe など）のパターンはなく、空間の形や配置の主張に候補がなければ文章にする
