# ステージ5: 主張を組み立てる（Claim Analysis）

フェーズ: インタビュー 5/6　成果物: `05-claims.json`　承認: 必要

## ねらい

文書で主張したいことを、**主張の中心（C0）→ それを支える主張 → 根拠となる事実**の木に分解します。
この木が、ステージ6の事実確認とステージ7の論理検証の対象になります。

## 進め方

1. `01-intent.md` の「伝えたいこと」を、検証できる程度に精密にして C0 にする。
2. C0 を支える主張を3つ前後に絞る（読者が一度に覚えておけるのは3〜4個まで。5個を超えると警告が出る）。
3. 各主張について、「なぜそう言えるのか」を掘り下げ、根拠になる**事実**を挙げる。
   - 事実は、誰かが確かめられる形で書く（「多くの人が困っている」ではなく「2025年の社内アンケートで回答者の62%が検索に不満と答えた」）。
   - まだ確かめていない事実でもよい。ステージ6で確かめる。
   - **傾向・頻度・原因の主張（「よく起きる」「主な原因は3つ」「多くの場合〜」）は、記録の全件を分類して数えた事実で支える。** `04-analysis.md` の「集計できる素材」にある素材ごとに、数えた結果を述べる事実を1つ以上挙げ、`dataset` にその名前を書く（例: 「取材した19のエピソードのうち、AI が頼んでいないものを足した場面が8件、意図が伝わらなかった場面が4件、誤りに気づかなかった場面が3件」）。まだ数えていなければ見込みの数字でよく、ステージ6で全件を分類して数え、statement を直す。1件の事例の事実は「起きうる」ことしか支えない。例として使う事実と、数えた事実を分ける。
   - **誰かの発言の記録（「筆者は〜と答えた」「部長は〜と言っている」）は、発言があったことの事実であって、内容が正しいことの根拠ではない。** 内容を根拠にするなら、内容そのものを事実にして確かめる（確かめられなければ、ステージ6で `user_asserted` になる）。発言を引用として使うだけなら、発言の記録のままでよい。
   - ユーザーの資料にある事実だけでなく、主張が頼っている**一般の事実**も挙げる。道具や規格の仕様（例: 「GitHub では、プルリクエストを出した本人は自分のプルリクエストを承認できない」）、公開の統計、研究で分かっていること。`04-analysis.md` の「不足している情報」で「調べればわかる」と印を付けたものは、ここで事実にする。`source_hint` に、どこで確かめられそうか（公式ドキュメント、論文など）を書く。ここで挙げておくと、ステージ6で調べられ、ステージ7で証拠のない前提（確信度 0.05）が減る。
4. 主張の種類（type）を付ける。
   - `fact`: 事実そのものを主張する / `judgement`: 事実から判断を導く / `proposal`: 行動を提案する / `explanation`: 仕組みや手順を説明する
5. `04-analysis.md` の「論点」に挙げた反論に、どの主張が答えるかを確かめる。答えられていない論点があれば、主張を足すか、ユーザーと相談して範囲外にする。
6. **主張の形（form）を決める。** 何かと何かを比べる主張ごとに、次のどちらの形で言うかをユーザーに選んでもらう。比べない主張は「能力の文」にする。
   - **能力の文（`capability`）:** 仕組みとして言い切れる形。例:「新しい検索では、保存した記事は5秒以内に検索に出る」。
   - **比較の文（`comparison`）:** 確率や件数で比べる形。例:「新しい検索のほうが、いまの検索より探し物にかかる時間が短い」。
   - 選んでもらう前に、日常語でこう伝える:「比べる言い方にすると、『どちらが多いか』を示すために、まだ確かめていない前提がたくさん要ります。そのぶん、言い切れる強さは上がりにくくなります。仕組みとしてできることを言う形なら、前提が少なく、強く言いやすくなります」。
   - この選択で、ステージ7の論証の深さが決まる。比較の文を選んだ主張があるときだけ、ステージ7で確率の世界を作る。
   - ステージ7から戻ってきたとき（主張の読みや形を直すとき）も、同じように説明してから選び直してもらう。
7. **主張の中心（C0）のメッセージ種別（message_kind）を決める。** 文書が読者に何を渡すかで、ステージ8の構成の型（PREP か SDS か、ADR か設計書か）が決まる。
   - proposal: 提言（判断や行動を求める）／ decision: 決定の記録／ report: 事実報告／ instruction: 手順指示／ explanation: 概念説明／ comparison: 比較評価／ education: 教育
   - 01-intent.md の「読後の行動」と 03-reader.json の purpose から、たいてい一つに決まる。迷ったらユーザーに聞く。
8. 主張の木を、読者の言葉で3〜5行にまとめてユーザーに見せ、「言いたいことはこれで合っていますか」と確かめる。主張の形の選択も、ここで一緒に確かめる。ユーザーが意図と違うと言ったら、ここで直す。

## 成果物 `05-claims.json`

```json
{
  "main_claim": {"id": "C0", "text": "主張の中心", "form": "comparison", "message_kind": "proposal",
                 "form_note": "ユーザーが、比べる言い方で伝えたいと選んだ", "premises": []},
  "claims": [
    {"id": "C1", "text": "C0を支える主張", "type": "judgement", "form": "capability", "supports": "C0", "premises": ["F1", "F2"]},
    {"id": "C2", "text": "C1をさらに支える主張", "type": "fact", "form": "capability", "supports": "C1", "premises": ["F3"]}
  ],
  "facts": [
    {"id": "F1", "statement": "検証できる形の事実", "source_hint": "どこで確かめられそうか"},
    {"id": "F2", "statement": "問い合わせ14件のうち、設定の誤りが9件、操作の誤りが3件、不具合が2件", "source_hint": "02-context/inquiries.md を全件分類する",
     "dataset": "問い合わせの記録"}
  ]
}
```

- `supports`: その主張が支える上位の主張の id。
- `premises`: その主張の根拠になる事実（F）や主張（C）の id。空にはできない。
- `form`: 主張の形。`capability`（能力の文）か `comparison`（比較の文）。主張の中心（C0）も含め、すべての主張に必須（ないと門で止まる）。`form_note` に、選んだ理由やユーザーの言葉を書いてよい。
- `message_kind`: C0 のメッセージ種別（上の7つのいずれか）。C0 にだけ付ける。
- `dataset`: 集計の事実。`04-analysis.md` の「集計できる素材」の名前。ステージ6で全件を分類して数え（`tally`）、CLI が数え直して照らす。表にある素材に `dataset` の事実がないと警告（GT045）、表にない名前はエラー（GT046）。
- id は C1, C2…／F1, F2… の形。循環は禁止（CLI が検出する）。

## 完了条件

- `cyrus check` でエラーが0。
- 主張の木の要約をユーザーに見せて承認をもらい、`cyrus advance --confirmed "…"`。
