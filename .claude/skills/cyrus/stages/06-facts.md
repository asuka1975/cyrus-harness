# ステージ6: 事実を確かめる（Fact Verification）

フェーズ: インタビュー 6/6　成果物: `06-facts.json`　承認: 不要（反証が出たらユーザーに報告する）

## ねらい

`05-claims.json` の事実（F）を、外部の信頼できる情報源や、あなた自身が実行・計測することで確かめます。
ここで決まる `status` が、ステージ7で公理と主張の確信度を計算するときの土台になります。

## 進め方

1. 雛形 `06-facts.json` には、すべての事実が `unverified` で並んでいる。
2. 事実を性質で分け、確かめ方を決める。
   - 公開情報で確かめられる → `cyrus-fact-checker` サブエージェントに任せる（複数の事実をまとめて渡してよい。独立した事実のグループは並列に起動してよい）
   - コードやデータを実行すれば確かめられる → あなたが実行し、コマンドと結果を `evidence` に書く（method: `execution`）
   - 社内の数字など、ユーザーにしかわからない → ユーザーに出典を聞く。出典のない証言は `user_asserted`
   - 論理的に導けるだけ → `reasoning`（status は `unverified` か `partially_verified` にとどめる）
3. サブエージェントには、事実の id と statement、`source_hint`、読者の知識レベルを渡し、次の JSON の形で返してもらう。
4. 結果をまとめ、`06-facts.json` に反映する。
5. **反証（refuted）が出たら、すぐユーザーに報告する。** 主張の見直しが必要なので `cyrus back claims` で戻る。事実の言い方を正確にすれば成り立つ場合（例: 「半分」→「4割」）は、05-claims.json の statement を直して戻ってくる。

## status の基準

| status | 意味 | 確信度 |
| --- | --- | --- |
| `verified` | 信頼できる一次情報源、または実行結果で確認できた | 0.95 |
| `partially_verified` | 一部だけ、または間接的に確認できた | 0.75 |
| `user_asserted` | ユーザーの証言のみ | 0.60 |
| `unverified` | 確認できていない | 0.05（証拠がないのと同じ） |
| `refuted` | 誤りだと確認した | 0（使えない） |

`confidence` を明示すると、この表の値より低い値を付けられます（高くはできません）。

## 成果物 `06-facts.json`

```json
{
  "facts": [
    {
      "id": "F1",
      "statement": "事実（検証の結果、言い方を正確にしたもの）",
      "status": "verified",
      "method": "web | document | execution | user | reasoning",
      "sources": [{"title": "資料名", "url": "https://…", "accessed": "2026-09-28", "quote": "該当箇所の短い引用"}],
      "evidence": "method が execution のとき: 実行したことと結果",
      "notes": "確認できた範囲、注意点",
      "axioms": ["ステージ7の手戻りで集めた事実なら、その公理の名前（省略可）"]
    }
  ]
}
```

## ステージ7からの手戻り（`cyrus back facts` で戻ってきたとき）

ステージ7（論理を検証する）は、論証に使う公理のうち、確信度が 0.4 未満のものと、反対の証拠があるもの（`@against`）を**手戻りの一覧**として出します。
その公理を支える事実を集めるために、ここへ戻ってきます。`cyrus status` の履歴に「ステージ7の手戻り」とあれば、この場合です。

### 1. 一覧を読む

- `07-logic/report.json` の `rework` が一覧です。項目ごとに次のことが書いてあります。
  - `axiom`: 公理の名前。`confidence`: いまの確信度。`reasons`: `low_confidence`（確信度が低い）か `against`（反対の証拠がある）。
  - `claims`: この公理が値を決めている主張。`support`・`against`: いま付いている事実。
- 公理の中身は `07-logic/Argument.lean` の、その名前の `axiom` の直前の docstring にあります。とくに「要ファクト:」（集めるべき事実）、「弱い点:」、論拠を読みます。
- `07-logic/review.md` の「反対の証拠の候補」に、Reviewer が見つけた、まだ事実として登録されていない反対の証拠が書いてあります。
- 扱う順:
  1. 前の周の差分の設計書（`07-logic/rounds/<最後の周>/model-plan-delta.md` の「ステージ6で確かめること」）や review.md に、確かめる順が書いてあれば、それに従います。Planner と Reviewer は、どの公理が主張を意味の上で左右するかを見ています（`report.json` の `claims` は証明の上の依存だけなので、意味の上で効く公理を拾いきれないことがあります）。
  2. 書いていなければ、`report.json` の `weak_premises`（主張の中心 C0 の値を決める公理が先）、次に `claims` が空でないもの、の順にします。`claims` が空のもの（不利な結論の定理だけが使うものなど）は後回しでかまいません。
- 一覧が多いときは、「要ファクト:」が同じ公理（同じ量を方式ごとに置いたものなど）をまとめ、1つの質問・1つの事実で扱ってかまいません（事実の `axioms` に複数の公理を書きます）。

### 2. 公理ごとに集め方を決めて、集める

| 公理の中身 | 集め方 |
| --- | --- |
| 社内の事情や数字など、ユーザーにしか分からない | **ヒアリング。** 一覧のうちユーザーに聞くものを、まとめて1回で聞く。「〜という前提で書いています。実際はどうですか」の形にする。出典（記録や資料）があれば一緒にもらう |
| 手元で実行・計測・数えれば分かる | **実験。** あなたが実行し、コマンドと結果を `evidence` に書く（method: `execution`） |
| 公開情報で確かめられる | **調査。** `cyrus-fact-checker` に任せる |

- ヒアリングの言葉は、聞く相手（ユーザー）の言葉に合わせます。ハーネスの言葉（公理、確信度、門、ステージなど）は使いません。製品名や社内の用語は、ユーザーが使っているなら使ってかまいません。
- ユーザーが別の人（情報システム部や経理など）から聞いて伝えた答えは `user_asserted`、その人の記録や資料をもらえたら `document`（`sources` の `location` に置き場所）にします。返事を待つ期限をユーザーと決め、期限までに来なければ「5. 集められなかった公理」として扱います。
- 実験の環境やログがユーザーの手元にしかないときは、ユーザーに頼みます。ユーザーが測った結果は、記録（ログやファイル）をもらえたら `document`、口頭だけなら `user_asserted` にします。
- ステージ5で直すこと（主張の言い回しや形の問題。review.md で戻す先がステージ5の指摘）は、このヒアリングでは聞きません。ステージ7の終わりにまとめて扱います。ユーザーがそれについて話したら、メモしておき、ステージ7に戻ったときに渡します。
- 03-reader.json などの成果物から推測した反対の証拠の候補は、そのまま事実にせず、ユーザーに確かめてから登録します。

### 3. 事実として登録する

- 集めた事実は、06-facts.json に**新しい ID** で登録します（いまの最大の番号の次。1つの事実を分けるなら `F26a` のような枝番）。status・method・sources は、上の「status の基準」のとおりに付けます。
- `axioms` に、その事実を集めた公理の名前を書きます（例: `"axioms": ["noHit_same"]`）。ステージ7の Planner が、どの公理の `@support`・`@against` に使うかを知るためです。`axioms` のある事実は、05-claims.json になくても警告になりません。公理の名前が Argument.lean にないと、警告が出ます。
- 社内の素材を出典にするときは、`sources` に `{"title": "聞き取りメモ", "location": "02-context/sources.md 聞き取りメモ"}` のように `location` を書きます（`url` の代わり）。
- review.md の「反対の証拠の候補」も、確かめて事実として登録します。登録すると、ステージ7の Reviewer が `@against` を付けられるようになります。

### 4. 明らかに誤っている公理を棄却する

集めた事実で、公理が明らかに誤りだと分かったら、棄却します。

1. 誤りだと示す事実を、06-facts.json に登録する。status は、その事実が確かめられた度合い（`verified` など）です。`refuted` は「事実の文そのものが誤り」のときに使うもので、公理を否定する事実には使いません。
2. 棄却することを、理由と一緒にユーザーに伝える（主張が弱まることがあるため）。
3. `07-logic/rejected.json` に記録する（ファイルがなければ作る）。`axiom` は Argument.lean に書いた名前（名前空間なし）です。

```json
{
  "rejected": [
    {"axiom": "noHit_same", "reason": "F12: 置き換えの前後で、検索結果が0件になる割合が2倍に増えた", "facts": ["F12"], "rejected_at": "2026-10-01"}
  ]
}
```

Argument.lean の公理は、ここでは消しません。ステージ7に戻ると、棄却した公理が残っているので門で止まります（LG009）。それを合図に、ステージ7の局所修正で公理を消し、それに依存していた定理を直します。
棄却で主張の中心（C0）などが示せなくなりそうでも、まずステージ7に戻ります。示せなくなったと分かったら、ステージ7からステージ5に戻ります（`cyrus back claims`）。そのことを、先にユーザーに伝えておきます。

### 5. 集められなかった公理

- 期限や手段の都合で集められなかった公理も、記録を残します。notes に「何を試し、なぜ集められなかったか」を書いた事実（status `unverified`）を登録し、`axioms` にその公理を挙げます（まとめて1件でよい）。手戻りの一覧の公理のうち、事実の `axioms` にも `rejected.json` にもないものがあると、`cyrus check` が警告します（手をつけていない公理と区別するため）。
- 一覧の公理のうち、集められなかったものと、その公理が値を決める主張を、日常語でユーザーに伝えます。「この前提は確かめられなかったので、本文では〇〇は可能性として書きます」。ユーザーが「このまま進める」と判断したら、それでかまいません。

### 6. ステージ7に戻る

（`cyrus` は SKILL.md のとおり、`python3 .claude/skills/cyrus/scripts/cyrus.py` のことです）

1. `cyrus check` でエラーが0、警告がない（手戻りの一覧のすべての公理に扱いが記録されている）ことを確かめ、`cyrus advance` でステージ7に戻る。`07-logic/` のファイルはそのまま残っています。
2. ステージ7のガイドの「手戻りから戻ったとき」に従って、局所修正の周を始めます。Planner には、新しく登録した事実（`axioms` 付き）と `rejected.json` を渡します。
   - 事実が集まった公理は、名前を変えて新しい公理として書き直し、`@support` に新しい事実を付けます（前の公理に付いていた `@reviewer` は引き継ぎません）。Reviewer が新しい公理を改めて監査します。確信度を上げる道は、これだけです。
   - 3周の上限は、戻ってきたところから数え直します。

## 完了条件

- `cyrus check` でエラーが0になったら `cyrus advance`。
- 反証や大きな修正があった場合は、その内容を1〜2行でユーザーに伝えてから進む。
- ステージ7からの手戻りで戻ってきたときは、一覧の公理ごとに、集めた事実・棄却・集められなかったことのどれかが決まっている。
