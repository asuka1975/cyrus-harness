# ステージ6: 事実を確かめる（Fact Verification）

フェーズ: インタビュー 6/6　成果物: `06-facts.json`　承認: 不要（反証が出たらユーザーに報告する）

## ねらい

`05-claims.json` の事実（F）を、外部の信頼できる情報源や、あなた自身が実行・計測することで確かめます。
ここで決まる `status` が、ステージ7で公理と主張の確信度を計算するときの土台になります。

## 進め方

1. 雛形 `06-facts.json` には、すべての事実が `unverified` で並んでいる。
2. 事実を性質で分け、確かめ方を決める。
   - 公開情報で確かめられる → `cyrus-fact-checker` サブエージェントに任せる（複数の事実をまとめて渡してよい。独立した事実のグループは並列に起動してよい）。**広く共有されているか（よくある言い方か、多くの人が同じ経験をしているか）も公開情報で確かめる。引用1つではなく、数えて確かめる**（下の「数えて確かめる命題」）
   - コードやデータを実行すれば確かめられる → 実験する（下の「実験を設計して行う」）。手元にあるもの（`02-context/` の素材、リポジトリ、ログ、モデル、スクリプト）で試せるなら、ユーザーに頼まず自分で行う。コマンドと結果を `evidence` に書く（method: `execution`）
   - 人の判断でしか決まらない（自然か、読みやすいか、どちらを選ぶか）→ 評価の問いにする（下の「人の判断を測る」）。ユーザーに例を考えてもらうのではなく、判定してもらう項目をこちらで用意する
   - 社内の数字や事情など、ユーザーにしかわからない → ユーザーに出典を聞く。出典のない証言は `user_asserted`（`private: true`）。**世の中について述べる証言（「みんなそう言っている」「定番だ」「普通の表現だ」）は、証言のままにしない。** 同じ内容を公開情報や手元の記録で確かめた事実を別に置き、証言の `checked` にその id を書く（どちらもないと警告 GT156）
   - 論理的に導けるだけ → `reasoning`（status は `unverified` か `partially_verified` にとどめる）
   - **`04-analysis.md` の「調べればわかること」から来た事実（`lookup` のある事実）は、必ずここで調べる。** 調べずに `unverified` のまま進めない
3. **05 の事実にないが、主張が頼っている一般の事実を調べて足す。** 次のものを拾い、`cyrus-fact-checker` に「命題の証拠を探す」仕事（B）として渡す（命題を日常語で、どの主張のためかと一緒に）。見つかった事実は、新しい id（いまの最大の番号の次）で `06-facts.json` に登録し、`claims` に支える主張の id を書く。05-claims.json は変えなくてよい（`claims` のある事実は、05 になくても警告にならない）。
   - `04-analysis.md` の「不足している情報」で「調べればわかる」と印を付けたもの
   - 主張（とくに judgement・explanation）が暗黙に頼っている、道具や規格の仕様（例: 「GitHub では、プルリクエストを出した本人は自分のプルリクエストを承認できない」）、公開の統計、研究で分かっていること（例: 一度に見せる確認が多いほど見落としが増える、という認知負荷の知見）
   - `03-reader.json` の読者像のうち、主張が頼る読者の能力・知識（例: 「新人は Git で commit と push ができる」）。ユーザーの発言に基づくので、`user_asserted`・method `user` の事実として登録してよい（`sources` の `location` に `03-reader.json`）
   ここで足しておくと、ステージ7で証拠のない【仮定】（確信度 0.05）が減り、手戻りが小さくなる。調べれば分かることを、ステージ7まで持ち越さない。
4. **集計の事実（`dataset` のある事実）は、記録の全件を分類して数える**（下の「記録の集まりを数える」）。1件や数件を読んで「〜という例があった」で済ませない。
5. サブエージェントには、事実の id と statement、`source_hint`、読者の知識レベルを渡し、次の JSON の形で返してもらう。
6. 結果をまとめ、`06-facts.json` に反映する。
   - **発言の記録は、発言があったことの事実です。** 「筆者は〜と答えた」「部長は〜と言っている」が `verified` になるのは、その発言が記録にあるときで、内容が正しいことは確かめていません。内容を主張の根拠にするなら、内容そのものを statement にした事実を別に置き、確かめます。確かめられなければ `user_asserted`（ユーザーの証言）か `unverified` です。発言の記録のままで内容の根拠にすると、ステージ7の Reviewer が確信度を下げます。
7. **反証（refuted）が出たら、すぐユーザーに報告する。** 主張の見直しが必要なので `cyrus back claims` で戻る。事実の言い方を正確にすれば成り立つ場合（例: 「半分」→「4割」）は、05-claims.json の statement を直して戻ってくる。

## 記録の集まりを数える（集計）

`04-analysis.md` の「集計できる素材」にある素材は、1件を選んで引用するのではなく、**全件を分類して数えます**。「十数件のうち n 件が A、m 件が B」という形の事実が、傾向・頻度・原因の主張を支えます。1件の事例は、そのあとで例として使います。
分類（記録ごとにどれに当たるかの判断）は LLM が、数えるのは CLI が受け持ちます。門は、CLI が数え直した値と `tally` を照らします。

1. **分類の基準を決める。** 「数える観点」（04 の表）と、支える主張から、分類の名前と1行の定義を決める。分類は互いに重ならないようにし、どれにも当たらない記録のために「該当なし」を置く。1つの記録が2つの分類に当たる基準なら、そう決めておく（`counts` の合計が `total` を超えてよい）。
2. **`cyrus-fact-checker` に「記録を分類して数える」仕事（C）を渡す。** 渡すものは、素材の名前と置き場所、単位、件数、分類の基準、表の保存先（`02-context/tally-<名前>.md`）。fact-checker は全件を読み、記録1件に1行の表（`| # | 記録 | 分類 | 根拠 |`）を書く。記録を飛ばさない（分からない記録も「該当なし」か「判断できず」で行を残す）。
3. **`cyrus tally 02-context/tally-<名前>.md` で数える。** 件数（`total`）と分類ごとの数（`counts`）が出る。分類が空の行があれば止まる。
4. **事実として登録する。** statement を数えた結果の文にし（「19件中8件（約4割）」）、`dataset`・`tally`（`items`・`total`・`counts`・`criteria`）を書く。method は `execution`、evidence に `cyrus tally` の結果を写す。status は、記録が一次資料（ログ、チケット、回答そのもの）なら `verified`、誰かが要約した記録（取材メモ、議事録）なら `partially_verified`（notes にそう書く）。分類に迷った記録は notes に挙げる。
5. 門（`cyrus check`）が `tally` を数え直す。`total`・`counts` が表と合わないとエラー（GT152）、04 の件数と合わないと警告（GT153）。statement の数字も `tally` に合わせる。

```json
{
  "id": "F2", "statement": "問い合わせ14件のうち、設定の誤りが9件、操作の誤りが3件、不具合が2件だった",
  "status": "verified", "method": "execution", "dataset": "問い合わせの記録",
  "tally": {"items": "02-context/tally-inquiries.md", "total": 14, "counts": {"設定の誤り": 9, "操作の誤り": 3, "不具合": 2},
            "criteria": "設定の誤り: 設定値を直せば解決した。操作の誤り: 手順どおりに操作し直せば解決した。不具合: 修正のコミットがある"},
  "evidence": "cyrus tally 02-context/tally-inquiries.md → total 14、設定の誤り 9、操作の誤り 3、不具合 2",
  "sources": [{"title": "問い合わせの記録", "location": "02-context/inquiries.md"}],
  "notes": "#7 は設定と操作の両方に見えたが、設定を直して解決したので設定の誤りにした"
}
```

数えた結果を文書に書くときは、割合と件数を先に出し、数え方（分類の基準）を一言添え、そのあとに例を1つ書きます（ステージ11）。値が5つ以上なら、ステージ10で表か図の候補になります。

## 数えて確かめる命題（広く共有されているか）

「〜はよくある言い方だ」「〜で困る人は多い」「〜は AI の定番の言い回しだ」「〜は普通の表現だ」のような命題は、引用を1つ見つけても決まりません。**数えて確かめます。** ユーザーが「検索すればいくらでも出てくる」「疑問を持つ人はいない」と言ったら、それは証言ではなく、数える仕事の依頼です。

- **意味の裏付け:** 辞書・用語集・公式の用語集に、その語義や用例がある。
- **頻度の裏付け:** 独立した用例・指摘の件数を数える。当たる先は、コーパス（少納言・BCCWJ、手元の学習データ）、検索（独立した記事・投稿）、手元の記録（`02-context/` にあるログやリポジトリ。fact-checker に場所を渡し、Grep で数えてもらう）。探した語句、当たった範囲、件数、日付を `evidence` に残す。
- **目安を先に決める。** 命題と一緒に、何件あれば支えるとみなすかを fact-checker に渡す（例: 「辞書に語義があり、コーパスで50件以上」「独立した指摘が3件以上」）。目安を決めずに探さない。反対の向き（違和感を書いた人の数、など）も同じ目安で数えてもらう。
- **status:** 意味と頻度の両方が目安に届けば `verified`、片方なら `partially_verified`。「その文字列そのものが辞書にない」「名指しの記事がない」だけでは下げない。命題は言い方の種類についてのことで、文字列の一致ではない。

## 実験を設計して行う（［実験］）

実行・計測・数えれば分かる命題は、ユーザーに頼む前に、あなたが設計して行います。

1. **設計を書く。** 何を測るか。何で測るか（手元の道具とデータ: `02-context/` の素材、リポジトリのスクリプトやモデル、ログ、`cyrus tally`）。命題が成り立つなら何が出て、成り立たないなら何が出るか（目安）。
2. **手元で試せるなら行う。** `cyrus-fact-checker` の「実験する」仕事（D）に、設計と場所を渡す（あなたが実行してもよい）。コマンドと結果を `evidence` に書き、method は `execution`。ファイルを書き換えるコマンドや、外部に影響するコマンドは使わない。
3. **手元にないものが要るなら、設計をユーザーに見せる。** 本番の環境、計測器、ほかの人の時間が要るときは、設計（何を、どう測るか）を添えて、ユーザーが行うか、このまま進めるかを決めてもらう。ユーザーが測った結果は、記録をもらえたら `document`、口頭なら `user_asserted`。
4. **試せなかったら「集められなかった」にする。** notes に、設計と、足りなかったものを書く。設計を書かずに「集められなかった」にしない。

## 人の判断を測る（評価の問い）

命題が人の判断で決まるとき（「この言い回しは不自然か」「この説明は読みやすいか」「同じ語のペアでも、文脈で自然にも不自然にもなる文があるか」）は、ユーザーに例を考えてもらうのではなく、**あなたが判定してもらう項目を用意し、評価の問いとして投げます。** これも実験の一種です（札は ［実験］）。

1. **項目を作る。** 命題が成り立つなら判定が分かれるはずの項目を5〜10件。あなたが作るか（例: 同じ語のペアを含む、自然な文と不自然な文の候補）、記録から選ぶ。
2. **問いを作る。** 項目ごとに同じ選択肢（自然／どちらとも言えない／不自然、など）で答えてもらう。1回で聞く（AskUserQuestion か、番号付きの一覧）。判定の基準（何を不自然と呼ぶか）を一言添える。
3. **答えを記録にする。** 項目1件に1行の表（`02-context/tally-<名前>.md`。「分類」の列が答え）に書き、`cyrus tally` で数え、`dataset`・`tally` 付きの事実にする（「10件中7件を不自然と判定した」）。判定者がユーザー1人なら、status は `user_asserted`（`private: true`。筆者の判断）。読者に近い人の判定をユーザーに集めてもらえたら `document`（`partially_verified`）。
4. **道具の出力と並べる。** 同じ項目に対するモデルや道具の出力が取れるなら、並べて事実にする（実験）。人の判定と道具の判定のずれが、そのまま主張の根拠になる。

## status の基準

| status | 意味 | 確信度 |
| --- | --- | --- |
| `verified` | 信頼できる一次情報源、または実行結果で確認できた | 0.95 |
| `partially_verified` | 一部だけ、または間接的に確認できた | 0.75 |
| `user_asserted` | ユーザーの証言のみ。ユーザーにしか分からないこと（`private: true`）か、同じ内容を調べた事実を `checked` に持つ | 0.60 |
| `unverified` | 確認できていない | 0.05（証拠がないのと同じ） |
| `refuted` | 誤りだと確認した | 0（使えない） |

`confidence` を明示すると、この表の値より低い値を付けられます（高くはできません）。

## ステージ7からの手戻り（`cyrus back facts` で戻ってきたとき）

ステージ7（論理を検証する）は、論証に使う公理のうち、確信度が 0.4 未満のもの、反対の証拠があるもの（`@against`）、要ファクトが ［調査］ で確信度が 0.85（言い切れる水準）に届いていないものを**手戻りの一覧**として出します。
その公理を支える事実を集めるために、ここへ戻ってきます。`cyrus status` の履歴に「ステージ7の手戻り」とあれば、この場合です。

一覧の公理をユーザーに見せるのは、調査と実験を済ませてからです。調べる前に「証拠がない」「あなたの記憶だけが根拠です」とは言いません。言えるのは、何を探して何が見つからなかったかが notes に残ってからです。

### 1. 一覧を読む

- `07-logic/report.json` の `rework` が一覧です。項目ごとに次のことが書いてあります。
  - `axiom`: 公理の名前。`confidence`: いまの確信度。`reasons`: `low_confidence`（確信度が 0.4 未満）、`research`（要ファクトが ［調査］ で、言い切れる水準 0.85 に届いていない。調査はユーザーの手を借りないので、届くまで調べる）、`against`（反対の証拠がある）。
  - `claims`: この公理が値を決めている主張。`support`・`against`: いま付いている事実。
  - `need`: 要ファクト（集めるべき事実）。`how`: 集め方（`調査`＝公開情報で確かめる／`実験`＝実行・計測／`ヒアリング`＝ユーザーに聞く）。Writer が要ファクトの先頭に付けた札で、なければ `null`。`null` のものは、下の表の基準であなたが分けます（公開情報で確かめられるなら、必ず調査）。
- 公理の中身は `07-logic/Argument.lean` の、その名前の `axiom` の直前の docstring にあります。とくに「要ファクト:」（集めるべき事実）、「弱い点:」、論拠を読みます。
- `07-logic/review.md` の「反対の証拠の候補」に、Reviewer が見つけた、まだ事実として登録されていない反対の証拠が書いてあります。
- 扱う順:
  1. 前の周の差分の設計書（`07-logic/rounds/<最後の周>/model-plan-delta.md` の「ステージ6で確かめること」）や review.md に、確かめる順が書いてあれば、それに従います。Planner と Reviewer は、どの公理が主張を意味の上で左右するかを見ています（`report.json` の `claims` は証明の上の依存だけなので、意味の上で効く公理を拾いきれないことがあります）。
  2. 書いていなければ、`report.json` の `weak_premises`（主張の中心 C0 の値を決める公理が先）、次に `claims` が空でないもの、の順にします。`claims` が空のもの（不利な結論の定理だけが使うものなど）は後回しでかまいません。
- 一覧が多いときは、「要ファクト:」が同じ公理（同じ量を方式ごとに置いたものなど）をまとめ、1つの質問・1つの事実で扱ってかまいません（事実の `axioms` に複数の公理を書きます）。

### 2. 公理ごとに集め方を決めて、集める

順番は、**調査 → 実験 → ヒアリング** です。調査と実験はユーザーの手を借りずに済むので、先に済ませます。ユーザーに聞くのは、そのあとに残ったものだけです。

| 公理の中身 | 集め方 |
| --- | --- |
| 公開情報や手元の記録で確かめられる（道具や規格の仕様、公式ドキュメント、統計、論文や調査で分かっていること。**広く共有されているか**: よくある言い方か、多くの人が同じ経験をしているか。これは数えて確かめる） | **調査（必ず行う）。** 一覧のうち `how` が `調査` のもの（と、札がなくても公開情報で確かめられるもの）を、**1回の `cyrus-fact-checker` の呼び出しにまとめて渡す**（「命題の証拠を探す」仕事（B）。公理の名前、日常語の命題（docstring の1行目）、要ファクト、種類を渡す。数える命題なら、目安と、手元の記録の場所も渡す）。返ってきた事実を登録し、`for` が `against` のものは反対の証拠として登録する（Reviewer が `@against` を付けられるように）。`not_found` は「5. 集められなかった公理」として、探した範囲を notes に写す |
| 実行・計測・数えれば分かる。人の判断で決まる（自然か、読みやすいか、どちらを選ぶか） | **実験。** 上の「実験を設計して行う」のとおり、設計を書き、手元の道具で試す（fact-checker の「実験する」仕事（D）か、あなたが実行）。人の判断で決まる命題は、「人の判断を測る」のとおり、判定してもらう項目を用意して評価の問いを投げる。手元にないものが要るときだけ、設計を添えてユーザーに頼む |
| 社内の事情や数字など、ユーザーにしか分からない | **ヒアリング。** 一覧のうちユーザーに聞くものを、まとめて1回で聞く。「〜という前提で書いています。実際はどうですか」の形にする。出典（記録や資料）があれば一緒にもらう。世の中について述べる答え（「みんなそう言っている」「普通の表現だ」）は、証言として登録したうえで、同じ内容を調査に回す（証言の `checked` に、調査の事実の id） |

- 調べれば分かる前提を、調べずに「ユーザーがこのまま進める」で済ませないでください。確信度が 0.05 のまま残ると、ステージ11でその主張は仮説としてしか書けなくなります。
- ヒアリングの言葉は、聞く相手（ユーザー）の言葉に合わせます。ハーネスの言葉（公理、確信度、門、ステージなど）は使いません。製品名や社内の用語は、ユーザーが使っているなら使ってかまいません。
- ユーザーが別の人（情報システム部や経理など）から聞いて伝えた答えは `user_asserted`、その人の記録や資料をもらえたら `document`（`sources` の `location` に置き場所）にします。返事を待つ期限をユーザーと決め、期限までに来なければ「5. 集められなかった公理」として扱います。
- 実験の環境やログがユーザーの手元にしかないときは、ユーザーに頼みます。ユーザーが測った結果は、記録（ログやファイル）をもらえたら `document`、口頭だけなら `user_asserted` にします。
- ステージ5で直すこと（主張の言い回しや形の問題。review.md で戻す先がステージ5の指摘）は、このヒアリングでは聞きません。ステージ7の終わりにまとめて扱います。ユーザーがそれについて話したら、メモしておき、ステージ7に戻ったときに渡します。
- 03-reader.json などの成果物から推測した反対の証拠の候補は、そのまま事実にせず、ユーザーに確かめてから登録します。

### 3. 事実として登録する

- 集めた事実は、06-facts.json に**新しい ID** で登録します（いまの最大の番号の次。1つの事実を分けるなら `F26a` のような枝番）。status・method・sources は、上の「status の基準」のとおりに付けます。
- `axioms` に、その事実を集めた公理の名前を書きます（例: `"axioms": ["noHit_same"]`）。ステージ7の Planner が、どの公理の `@support`・`@against` に使うかを知るためです。`axioms` のある事実は、05-claims.json になくても警告になりません。公理の名前が Argument.lean にないと、警告が出ます。
- 社内の素材を出典にするときは、`sources` に `{"title": "聞き取りメモ", "location": "02-context/sources.md 聞き取りメモ"}` のように `location` を書きます（`url` の代わり）。
- review.md の「反対の証拠の候補」も、確かめて事実として登録します。登録すると、ステージ7の Reviewer が `@against` を付けられるようになります。

### 4. 明らかに誤っている公理を棄却する

集めた事実で、公理が明らかに誤りだと分かったら、棄却します。

1. 誤りだと示す事実を、06-facts.json に登録する。status は、その事実が確かめられた度合い（`verified` など）です。`refuted` は「事実の文そのものが誤り」のときに使うもので、公理を否定する事実には使いません。
2. 棄却することを、理由と一緒にユーザーに伝える（主張が弱まることがあるため）。
3. `07-logic/rejected.json` に記録する（ファイルがなければ作る）。`axiom` は Argument.lean に書いた名前（名前空間なし）です。

```json
{
  "rejected": [
    {"axiom": "noHit_same", "reason": "F12: 置き換えの前後で、検索結果が0件になる割合が2倍に増えた", "facts": ["F12"], "rejected_at": "2026-10-01"}
  ]
}
```

Argument.lean の公理は、ここでは消しません。ステージ7に戻ると、棄却した公理が残っているので門で止まります（LG009）。それを合図に、ステージ7の局所修正で公理を消し、それに依存していた定理を直します。
棄却で主張の中心（C0）などが示せなくなりそうでも、まずステージ7に戻ります。示せなくなったと分かったら、ステージ7からステージ5に戻ります（`cyrus back claims`）。そのことを、先にユーザーに伝えておきます。

### 5. 集められなかった公理

- 期限や手段の都合で集められなかった公理も、記録を残します。notes に「何を試し、なぜ集められなかったか」を書いた事実（status `unverified`）を登録し、`axioms` にその公理を挙げます（まとめて1件でよい）。手戻りの一覧の公理のうち、事実の `axioms` にも `rejected.json` にもないものがあると、`cyrus check` が警告します（手をつけていない公理と区別するため）。
- `調査` の公理は、調べる前に「集められなかった」にしません。notes には、探した語句と当たった情報源（`cyrus-fact-checker` の `not_found`）を書きます。
- `実験` の公理は、設計を書いて手元の道具で試す前に「集められなかった」にしません。notes には、設計と、足りなかったもの（環境、計測器、人の時間）を書きます。
- `ヒアリング` の公理は、尋ねる前に「集められなかった」にしません。notes には、何を聞いて何が返ったかを書きます。
- 集められなかった記録（`unverified` の事実）だけで扱った公理と、調べ残しのある ［調査］ の公理（`verified` の事実がまだ付いていない）が一覧に残っていると、`cyrus check`（GT155）と `cyrus lean`（LG041）が警告します。［調査］ は、言い切れる水準に届くか、調べ尽くす（探した範囲を notes に残し、ステージ7で Planner が要ファクトから ［調査］ を外す）まで続けます。`--accept-warnings` で進めるのは、ユーザーがそう決めたときだけです（判断が履歴に残ります）。
- 一覧の公理のうち、集められなかったものと、その公理が値を決める主張を、日常語でユーザーに伝えます。「この前提は確かめられなかったので、本文では〇〇は可能性として書きます」。ユーザーが「このまま進める」と判断できるのは、調査を済ませたあとに残った、実験とヒアリングの公理についてです。

### 6. ステージ7に戻る

（`cyrus` は SKILL.md のとおり、`python3 .claude/skills/cyrus/scripts/cyrus.py` のことです）

1. `cyrus check` でエラーが0、警告がない（手戻りの一覧のすべての公理に扱いが記録されている）ことを確かめ、`cyrus advance` でステージ7に戻る。`07-logic/` のファイルはそのまま残っています。集められなかった公理が残っていれば警告（GT155）が出るので、ユーザーが進めると決めたことを確かめてから `--accept-warnings` を付けます。
2. ステージ7のガイドの「手戻りから戻ったとき」に従って、局所修正の周を始めます。Planner には、新しく登録した事実（`axioms` 付き）と `rejected.json` を渡します。
   - 事実が集まった公理は、名前を変えて新しい公理として書き直し、`@support` に新しい事実を付けます（前の公理に付いていた `@reviewer` は引き継ぎません）。Reviewer が新しい公理を改めて監査します。確信度を上げる道は、これだけです。
   - 調査を尽くした公理（事実の notes に探した範囲がある）を書き直すときは、要ファクトに ［調査］ を残しません（残すと、言い切れる水準に届くまで一覧に入り続けます）。残る確かめ方（実験・ヒアリング）を書くか、【経験則】にします。
   - 3周の上限は、戻ってきたところから数え直します。

## 完了条件

- `cyrus check` でエラーが0になったら `cyrus advance`。
- 反証や大きな修正があった場合は、その内容を1〜2行でユーザーに伝えてから進む。
- ステージ7からの手戻りで戻ってきたときは、一覧の公理ごとに、集めた事実・棄却・集められなかったことのどれかが決まっている。
