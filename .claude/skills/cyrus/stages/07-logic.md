# ステージ7: 論理を検証する（Logical Structure Design）

フェーズ: 組み立て 1/5　成果物: `07-logic/` の一式（`Argument.lean`・`Model.lean`・`model-plan.md`・`review.md` など）　承認: 不要

## ねらい

主張を、Lean 4 で書いた**モデル**から定理として導きます。

1. 主張を説明するのに必要な**コンポーネント**（型・関数・定数）を宣言する。
2. コンポーネントどうしの関係を**関係公理**として書く。自明なこと、実験で確かめた事実、経験則、仮定を、根拠の種類ごとに区別する。
3. 主張したいことを**定理**として示す。

Lean がコンパイルすれば、公理から主張までの筋道は機械で保証されます。公理そのものの確からしさは**確信度**で表し、証拠の足りない公理はステージ6へ戻して事実を集めます。
主張の木を Lean の構文に写すだけ（中身のない命題と、それをつなぐ推論規則）では、何も保証しません。命題論理だけで書けると考えず、主張に必要なものをモデルとして組み立ててください。

このステージの判断のよりどころは、オーナーの原則（`references/owner-principles.md`）です。3役にも必ず渡します。
Lean の書き方の落とし穴は `references/lean-modeling.md` にあります。

## 「確信度」と「確率」の呼び分け

このステージには、確からしさを表す数が2種類出てきます。混ぜないでください。

| 呼び方 | 何の数か | どこにあるか | 例 |
|---|---|---|---|
| **確信度** | その公理が現実に成り立つと、どれだけ信じてよいか。証拠で決まる | 関係公理の docstring（`@confidence`）と `report.json` | 「Lean 方式の伝え間違いはドキュメント方式以下」という公理の確信度 0.05（証拠がない） |
| **確率** | モデルの中の量。現実の出来事が起こる割合を、モデルの登場人物として表したもの | `Argument.lean` の宣言と式（`Rat` や `Prob`） | 要件1件を伝え間違える確率 `missProb .lean` |

- 確信度は、公理が有利か不利かを表しません（オーナーの原則12）。向きの問題は Reviewer が別に見ます。
- 「確率が 0.3 以下」という公理の確信度が 0.6、ということがあります。2つは別の数です。
- 本文で主張をどこまで言い切るかは、主張の**確信度**で決まります（この文書の最後の表）。

## 役割

| 担い手 | やること | 書くファイル |
|---|---|---|
| **あなた（オーケストレータ）** | 役を呼び、入力を渡し、`cyrus` を実行し、打ち切りと手戻りを進める | なし（役に書かせる） |
| **Logical Model Planner**（`cyrus-logic-planner`） | コンポーネントと関係を設計する | `model-plan.md`（2周目から `model-plan-delta.md`）、比較の主張があれば `ledger.json` |
| **Lean Writer**（`cyrus-lean-writer`） | 設計書のとおりに Lean で書く。証人も書く | `Argument.lean`・`Model.lean`・`writer-note.md` |
| **Lean Logic Reviewer**（`cyrus-logic-reviewer`） | 敵対的に監査する。証拠を確かめられない公理の確信度を下げる | `review.md`。`Argument.lean` の `@confidence` の書き換えと `@reviewer`・`@against`・`@restates` の印 |
| **cyrus CLI（決定論）** | 形と存在の検査（門）、確信度の計算、手がかりの抽出、周の記録 | `report.json`・`hints.json`・`rounds/` |

決定論と確率の棲み分けは次のとおりです（オーナーの原則9・10）。

- **門（CLI）:** 形と存在だけを検査する。通らなければ先へ進めない。
- **手がかり（CLI）:** 中身の良し悪しを数で近似するもの。門にすると書き手がその数を動かすので、`hints.json` に出して **Reviewer にだけ**渡す。
- **中身の判断（Reviewer）:** 証拠が公理を意味の上で支えるか、公理が結論の言い換えか、比べ方が公平か。

## 流れ

### 1周目

1. **Planner を呼ぶ。** 入力は下の「役に渡すもの」のとおり。Planner は、主張ごとに論証の深さを決め（次の節）、`model-plan.md` を書く。比較の主張があれば `ledger.json`（失敗の台帳）も書く。
2. **Writer を呼ぶ。** Writer は `Argument.lean`・`Model.lean` を書き、`cyrus lean` の門のエラーが0になるまで直す。設計書と違う書き方をしたところは `Argument.lean` の冒頭の「設計書（model-plan.md）との違い」に書き、作業の報告は `writer-note.md` に書く。
3. **あなたが `cyrus lean` を実行し、門のエラーが0であることを確かめる。** エラーが残っていれば Writer に戻す。
4. **Reviewer を呼ぶ。** Reviewer は `review.md` を書く。1行目は「判定: 合格／条件付き合格／差し戻し（高 N・中 N・低 N）」の形にする。証拠を確かめられない公理は、`Argument.lean` の `@confidence` を下げ、`@reviewer` の行を足す。
5. **`cyrus lean` をもう一度実行する**（Reviewer の書き換えを確信度に反映し、門を確かめる）。
6. **`cyrus logic-round close` で周を閉じる。** いまのファイルが `07-logic/rounds/NN/` に写り、打ち切りが判定される（下の「打ち切り」）。
7. **高の指摘の戻す先がステージ5（主張の形や読み）なら、周を続けない。** 主張はユーザーが決めることなので、ステージ7の中では直せません。指摘を日常語でユーザーに見せ、`cyrus back claims` でステージ5に戻ります。戻す先がステージ6（事実の不足）の指摘は、周を続けてよく、ステージの終わりの手戻りで扱います。
   - 手順: `cyrus logic-round close` で周を閉じてから（記録を残す）、`cyrus back claims --reason "…"`。ユーザーが決めた主張の文を 05-claims.json に書き、ユーザーの答えを承認として `cyrus advance --confirmed "…"`。事実を足さないなら、ステージ6も `cyrus advance` で通り、ステージ7に戻る（`07-logic/` のファイルはそのまま残る）。
   - 戻ったら、次の周を局所修正として始める。Planner には、前の周の review.md と、ステージ5で決まったこと（新しい主張の文）を渡す。
   - 戻す先がステージ5の**中・低**の指摘は、周を止めない。ステージの終わりにまとめてユーザーに見せ、主張を変えるかを聞く。

### 2周目から（局所修正）

打ち切りでなければ、指摘を対応する役に戻します。全体を作り直さず、**局所修正**にします。

1. **Planner** が、前の周の `review.md` の指摘に答える差分の設計書 `model-plan-delta.md` を書く。`cyrus logic-round close` が雛形を置いている。「## 変更」の表に1行1つの変更を書き、変える宣言・公理・定理の名前を `` `名前` `` で挙げる（`cyrus logic-round diff` はこの表の行だけを対応表に使う）。採らない指摘は「## 採らない指摘」に理由を書く。
   - 公理の命題を変えるとき（型を変えるときも、型は同じでも使う宣言の意味を変えるときも）、公理を分けるときは、公理の名前を変えて別の公理にする（宣言の名前まで変える必要はない。宣言の意味を変えたら、宣言の docstring を直す）。前の公理の `@reviewer` の判断は、変えた命題には当てはまらないため引き継がない。Reviewer は新しい公理を改めて監査する（Reviewer は値を下げるだけなので、名前を変えずに命題を弱めると、値を見直す道がなくなる）。
   - 主張の読みが変わって要らなくなった公理・定理は、消すだけでよい（`rejected.json` は、明らかに誤りと分かった公理の記録）。消したことは「## 変更」に書く。
2. **Writer** が差分の設計書のとおりに直し、門を通す。`Argument.lean` の axiom 以外の行を直したら、`Model.lean` にも同じ変更を写す（写し忘れは門の LG022 で止まる）。`writer-note.md` を書き直す。
3. **あなたが `cyrus logic-round diff` を実行する。** 前の周から変わった宣言の一覧と、差分の設計書の各行が当たった宣言の対応表が `07-logic/diff.md` に、行ごとの差分の全文が `07-logic/diff.patch` にできる。
4. **Reviewer** が、差分・対応表・差分の設計書・前の周の `review.md` を監査し、`review.md` を書き直す。
5. `cyrus lean` と `cyrus logic-round close`。

### 打ち切り

`cyrus logic-round close` が、次のどちらかでループを止めます。

- **止める:** 高の指摘が0で、門のエラーが0で、どの主張の確信度も前の周から上がらなかった（1周目は、比べる周がないので上がった主張はないとみなす）。これ以上精密にしても値は上がりません。残りは事実の不足か主張の形の問題なので、ステージ6か5で扱います。
- **ユーザーに見せる:** 3周で止まらなかった。残った指摘を日常語でユーザーに見せ、判断を仰ぎます（続けるか、主張を変えるか、事実を集めるか）。

### ステージの終わり: 弱い前提を見せる

ループが止まったら、承認は求めずに、確からしさを左右する弱い前提をユーザーに見せます。

1. `cyrus lean` の出力（`report.json` の `weak_premises`）に、主張の確信度を決めている弱い公理が、多くの主張に効くものから順に5つまで出ます。
2. それを、公理の名前や専門用語を使わず、日常語で箇条書き5行以内にして見せます。例:「いまの論証は、次の前提に頼っています。どれもまだ確かめていません。・承認した人は、変更の中身を見てから承認している ・…」。
3. そのうえで、1問だけ聞きます。「ほかに、〇〇を決めているもの（左右しているもの）はありますか」（〇〇は主張の中心で言っている結果。例: 伝え間違いが起きるかどうか）。
   - 答えに、論証に入っていない関係があれば、Planner に渡して局所修正の周を1つ回します（根拠がなくても、論証に必要なら公理として置く）。
4. ステージ5に戻す中・低の指摘（review.md）があれば、ここで一緒に日常語で見せ、主張を変えるかを聞きます。

### ステージの終わり: 手戻り

1. `07-logic/report.json` の `rework` に、手戻りの一覧が出ます。確信度が 0.4 未満の公理と、`@against` の付いた公理です。主張の定理が使わない公理（不利な結論の定理だけが使うものなど）も入ります。
2. 一覧が空でなければ、`cyrus back facts --reason "ステージ7の手戻り"` でステージ6に戻ります。そこで何をするかは、ステージ6のガイドの「ステージ7からの手戻り」にあります（公理ごとのヒアリング・実験・調査、事実の登録、棄却と `rejected.json`、ステージ7への戻り方）。
3. 一覧が空になるか、ユーザーが「この確信度のまま進める」と判断したら、`cyrus advance`。確信度の低い主張は、ステージ11で仮説として書きます。

### 手戻りから戻ったとき

ステージ6で事実を集めて `cyrus advance` で戻ってきたら、局所修正の周を始めます。

1. `cyrus lean` を実行する。棄却した公理（`rejected.json`）が残っていれば、門（LG009）で止まる。それでよい（次の周で消す）。
2. **Planner** に、前の周の review.md に加えて、新しく登録した事実（06-facts.json の、`axioms` の付いた事実）と `rejected.json` を渡し、差分の設計書を書いてもらう。
   - **事実が集まった公理は、名前を変えて新しい公理として書き直す。** `@support` に新しい事実を付け、前の公理に付いていた `@reviewer` の行は引き継がない。Reviewer は値を下げるだけなので、確信度を上げる道はこれだけ（オーナーの決定）。
   - 反対の証拠が登録された公理は、そのままにして Reviewer に `@against` を付けてもらうか、命題を正して名前を変える。
   - 棄却した公理は消す。それに依存していた主張の定理が示せなくなったら、周を止めてステージ5に戻る（`cyrus back claims`）。
3. Writer、`cyrus logic-round diff`、Reviewer、`cyrus logic-round close` は、2周目からと同じ。3周の上限は、戻ってきたところから数え直す（`logic-round close` が「このループの N 周目」と出す）。

## 論証の深さは、主張の形で決まる

主張には2つの形があります。

- **能力の文:** 決定論で言える形。例:「新しい検索では、保存した記事は5秒以内に検索に出る」。
- **比較の文:** 確率や件数で比べる形。例:「新しい検索のほうが、いまの検索より探し物にかかる時間が短い」。

**比較の文の主張があるときだけ、確率の世界（層・確率・「同じとみなす」判断・失敗の台帳）を作ります。** 能力の文だけなら、決定論の世界（Prop と Bool）だけで組みます。
比較の文は、量ごとに両方式の値・大小の向き・「同じとみなす」判断が要るので、判断の数が増え、確信度が上がりにくくなります。
主張の形は、ステージ5でユーザーが選び、05-claims.json の `form`（`capability`／`comparison`）に書いてあります。Planner はそれに従い、`model-plan.md` の1節に写します。形を変えたほうがよいと Planner や Reviewer が考えたら、ステージ5に戻す指摘にします（ユーザーが決めること）。

- **能力の文だけのとき:** 「同じとみなす」置き方、失敗の台帳（`ledger.json`）、`@baseline` の定理は要りません。`model-plan.md` の4節と6節には「比較なし」と書きます。ただし、主張が成り立たない場合や条件（不利な結論）は、能力の文でも定理として導きます。
- **主張の文が2通りに読めるとき:** どちらの読みかはユーザーが決めることなので、ステージ5で確かめます。確かめるまでは、両方の読みに `@claim` の定理を置きます（主張の確信度は小さいほうになります）。

## Writer の約束

- `def` は計算の手順だけに使う。現実についての判断は、「宣言」と「関係公理」に分ける。
  - 文書が定義する語や手順（例:「決められた流れ」とは何か）は `def` にしてよい。語の定義であって、現実についての判断ではないから。現実がその定義を満たすかどうかは、関係公理にする。語彙を並べる `inductive`（操作の種類など）もよい。
- 判断を、定理の引数、宣言の型、比較相手の定義、計算の def の docstring に置かない。
- 両方式の式に現れる量は、方式を引数に取る。「同じとみなす」なら【仮定】の関係公理にし、理由と向きを書く。
  - もともと方式に関係しない定数（会社の人数、人件費の単価など）は、方式を取らなくてよい。手がかりに出ることがあるが、Reviewer が判断する。
- 論証に必要な関係は、確信度が低くても省かない。要ファクトを付ける（オーナーの原則4）。確信度の低い【経験則】【実験】にも、要ファクトを書いてよい（ステージ6の手戻りで使う）。
- 読者についての前提（「commit と push ができる」など）も、06-facts.json に事実として登録されていなければ【仮定】にする。03-reader.json は読者像であって、事実の出典ではない。
- 見た目の違いを結果に直接結ばず、間で決めている量（例: 認知負荷）を宣言として挟む（原則5）。
- 比べる主張は、測れる量（件数は `Nat`、確率は `Rat` か `Prob`）の不等式で書く。「以下」と「真に少ない」を分ける（原則3）。
- 確率は、層ごとの「起こらない確率」の積の余事象で合成する。独立性は関係公理として明示する（原則6）。
  - 層ごとの確率を「前の層を通ったときの条件付き確率」として宣言すれば、積は連鎖律で決まり（【自明】）、独立性の公理は要らない。その代わり、条件付き確率の値ごとに判断が要る。どちらの組み方かを設計書に書く。
- 「同じとみなす」は、証明に要る向きの不等式だけを置いてよい（`≤` か `≥` の片側）。等式にすると、使わない向きまで仮定することになり、片方の向きの反証で全体が崩れる。両側の不等式を置くと、公理系の全体では等式と同じになる。両側が本当に要るか（別々の定理が別の向きを使うか）を確かめる。
- 比べる相手は、現実の相手にする。
- 不利な結論も定理として導く。有利な向きの仮定を経由しない経路を選ぶ。
- 主張の定理に前提（`P → Q` の `P`）があるなら、その前提が公理から否定できないことを確かめ、証人でも前提が成り立つ例を持たせる。証人 `Model.lean` の末尾に、前提が成り立つことを示す `example` を足して記録する（足してよい。足してはいけないのは `instance`・`attribute`・`open`・`set_option` だけ）。前提がいつも偽の定理は、何も言っていない（Lean はそれでもコンパイルし、`#print axioms` は証明の道筋の公理を出すので、機械では気づけない）。
- 主張を示す定理に `@claim C…` を付ける。主張の中心（C0）も含め、05-claims.json のすべての主張に1つ以上置く。主張より強い定理は `@beyond C…`、比べる相手を確かめる定理は `@baseline` にする。`@beyond` の定理は、文書で使わないなら置かない。`@baseline` は、相手が藁人形でないことを【自明】でない判断から示すときに置く（【自明】の公理を言い換えるだけなら置かない）。
- 不利な結論の定理は、本文で限界として主張するなら、ステージ5で主張（例:「この方式の限界」）にしてもらい `@claim` を付ける。主張にしないなら印を付けず、docstring の先頭に `[不利]` と書く。印のない定理も、CLI が `report.json` の `other_theorems` に確信度と依存する公理を出す。`[不利]` の定理には `unfavorable: true` が付く。これらは、主張の値にも、公理の使用の手がかりにも数えない。
- 「モデルの外」とする理由に「測っていない」「記録がない」を使わない。それは要ファクト付きの公理にする（原則3・4）。
- 関係公理の型の最上位と `∀` の直下に `∧` を置かない。原子命題ごとに公理を分ける。
- 検査の警告を消すために、ラベルを変えたり、公理を省いたりしない。検査が誤っているなら、`writer-note.md` にそう書く。
- `@confidence` には案を書く。案であって値ではない（値は CLI が証拠から計算し、Reviewer が下げる）。支える事実がない【経験則】【仮定】は、案によらず 0.05 になる。案を 0.05 に書き換える必要はない（事実が集まったときの見込みとして残してよい）。
- `@reviewer`・`@against`・`@restates` の印は付けない、消さない（Reviewer だけが付ける）。ただし、設計書の指示で公理の名前を変えて別の公理にしたときは、新しい公理に前の `@reviewer` の行を写さない。
- `hints.json` は読まない（Reviewer のための手がかり）。

## 関係公理と定理の印

関係公理の docstring の先頭に、根拠の種類を書きます。

| 種類 | 意味 | 付ける情報 |
|---|---|---|
| 【自明】 | 定義や数学からほぼ必然に言える | 論拠を1行 |
| 【実験】 | 事実（実行・計測・文書）で確かめた | `@support F…` |
| 【経験則】 | 一般に成り立つと考えられるが、例外がありうる | `@support F…`、`@confidence`、論拠、弱い点 |
| 【仮定】 | 論証に必要だが、まだ証拠がない | 同上と「要ファクト:」 |

印の一覧です（CLI・ガイド・エージェント定義で共通）。印は docstring の**行の先頭**に書きます。CLI は行頭の印だけを読むので、説明の文の中に `@support` などの語が出ても印にはなりません。

| 印 | 付ける場所 | 付ける役 | 書き方と意味 |
|---|---|---|---|
| `@support F…` | 関係公理 | Writer | 支える事実の ID（06-facts.json）。枝番（`F26a`）も書ける。1行に並べてよい。ないときは「@support なし（理由）」（「なし」で始まる行の ID は支えとして読まれない） |
| `@confidence 0.x` | 関係公理 | Writer（案）、Reviewer（書き換え） | 確信度の案。【経験則】【仮定】では必須 |
| `論拠:` | 関係公理 | Writer | なぜ成り立つか |
| `弱い点:` | 関係公理 | Writer | どこで崩れうるか。関係する事実 ID も書く |
| `要ファクト:` | 【仮定】 | Writer | これから集める事実。ステージ6で使う |
| `@against F…` | 関係公理 | Reviewer | 反対の証拠。付けたら確信度も下げる。手戻りの一覧に入る。反対の証拠が 06-facts.json にまだないときは、確信度を下げたうえで review.md に「反対の証拠の候補」として書く。ステージ6で事実として登録してから `@against` を付ける |
| `@reviewer <値> ← <元の案> 理由: …` | 関係公理 | Reviewer | 確信度を下げた記録。周ごとに1行足す。2行目からの「元の案」は前の行の値。最後の行の値は `@confidence` と一致させる。`@confidence` のない公理（【自明】【実験】）を下げるときは、`report.json` のその公理の値を元の案にし、`@confidence` の行も足す |
| `@restates <公理> 理由: …` | 定理 | Reviewer | 証明が公理の言い換えだが、そのままでよいと判断した記録 |
| `@claim C…` | 定理 | Writer | 主張（の項）を示す定理。05-claims.json のすべての主張に1つ以上 |
| `@beyond C…` | 定理 | Writer | 主張より強いことを示す定理。主張の確信度には入れない |
| `@baseline` | 定理 | Writer | 比べる相手が藁人形でないことを確かめる定理。主張の確信度には入れない |

例:

```lean
/-- 【仮定】置き換えた後の、探し物1回あたりの時間は、いまより長くならない。
@support なし（両方の仕組みで測った記録はない）
@confidence 0.05
@reviewer 0.05 ← 0.5 理由: 支える事実がなく、F12 は反対の向きを示している
@against F12
論拠: 記事がすぐ検索に出るので、探し直しが減る。
弱い点: 言葉の引き方が変わると、見つからない探し物が増えうる（F12）。
要ファクト: 両方の仕組みで、探し物1回の時間を測る。 -/
axiom searchTime_full_le : searchTime .fullText ≤ searchTime .current
```

## 確信度の決まり方

| 担い手 | やること |
|---|---|
| Writer | `@confidence` に案を書く |
| CLI | 【自明】は 1。【実験】は支える事実の status の値の最小値。【経験則】【仮定】で `@support` がなければ、案によらず **0.05**。`@support` があれば、案と支える事実の値の小さいほう |
| Reviewer | `@support` の事実が意味の上でその公理を支えているかを確かめる。確かめられなければ 0.05 まで下げる。反対の証拠があれば `@against` を付けて下げる。明らかな誤りは棄却を提案する。【自明】に強い仮定が紛れていないかを見る |
| CLI | 公理の値 = 上の値と `@confidence`（Reviewer が書き換えたものを含む）の小さいほう。定理の値 = `#print axioms` に出る関係公理の値の最小値。主張の値 = その主張の `@claim` 定理の値の最小値 |

事実の status の値: verified 0.95、partially_verified 0.75、user_asserted 0.6、unverified 0.05、refuted 0。
0 近くを 0.05 にし、0 にしないのは、0 が「確実に誤り」を表すからです。誤りは棄却（公理を消す）で表し、「まだ証拠がない」と区別します。

## 門と手がかり

`cyrus lean`（`cyrus check` も同じ）が検査します。

**門（エラー。通らなければ先へ進めない）**
- Lean でコンパイルできる。`sorry`・`native_decide`・Mathlib の import がない。`axiom`・`theorem` を字下げしていない
- 無矛盾性: 証人 `Model.lean` に axiom が残っていない。元の axiom 以外のコードの行が同じ順で残っている。各 axiom と同じ名前・同じ型の定義がある。Lean 標準の3公理以外に依存しない。`instance`・`attribute`・`open`・`set_option` を足していない
- 05-claims.json のすべての主張に `@claim` の定理がある。印が存在しない主張を指していない
- 関係公理に【】の種類がある。`@support`・`@against` の事実 ID が 06-facts.json にある。【仮定】に「要ファクト:」、【経験則】【仮定】に `@confidence`、【実験】に `@support` がある
- 関係公理の型の最上位と `∀` の直下に `∧` がない
- `@reviewer` の値が `@confidence` と一致し、元の案以下で、行どうしがつながっている
- 棄却した公理（`rejected.json`）が再び現れていない。空の `inductive` がない

**手がかり（`hints.json`。Reviewer にだけ渡す）**
- 証明が公理の名前だけの定理（言い換えの候補）、依存する【自明】以外の原子（【実験】も数える）が1つだけの主張の定理
- どの主張の定理にも使われない公理
- 両方式の式に現れるのに、方式（`Method`）を引数に取らない宣言
- 「弱い点」に出る事実のうち `@support` にないもの、分けた事実の親番号の残り
- 失敗の台帳で、片方の方式の欄が空いている量
- 書きかけの印、設計書の表と計算した値の食い違い

機械では見つけられないことの例: 主張の定理の前提がいつも偽（公理から否定できる）で、定理が何も言っていない。これは Reviewer が見ます。

**`report.json` に出るもの:** 主張ごとの確信度と hedge、定理ごとの確信度と依存する公理、公理ごとの確信度、原子命題の数、手戻りの一覧、証人の検査結果。門のエラーがあっても、計算できる値は出ます。

## 原子命題の数

関係公理の型を、最上位と `∀` の直下の `∧` で分けたものを原子命題と呼びます。CLI は数えて報告するだけで、上限は置きません。
公理の数は、まとめれば幾らでも下げられるので、良いモデリングの物差しにしないでください。判断の数は主張の形で決まります。減らしたいなら、ステージ5で主張の形（能力の文）を選び直します。
`report.json` の `atoms` に合計・種類ごと・主張の定理が使う数・`@beyond`／`@baseline` だけが使う数が、主張ごとに「値を決める原子」と「筋道の原子」の数が出ます。

```json

  "methods": ["current", "fullText"],
  "rows": [

      "layer": "検索に出る",

```

## 確信度と本文の書き方

`report.json` の各主張には hedge（言い切りの強さ）が付きます。ステージ11で本文を書くときに従います。

| 確信度 | hedge | 書き方 |
|---|---|---|
| 0.85 以上 | assert | 言い切る |
| 0.6〜0.85 | moderate | 根拠を添えて控えめに（〜と考えられます） |
| 0.4〜0.6 | tentative | 可能性として（〜の可能性があります） |
| 0.4 未満 | hypothesis | 主張にせず、仮説・未確認事項として書く |
