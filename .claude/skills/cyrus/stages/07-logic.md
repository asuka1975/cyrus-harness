# ステージ7: 論理を検証する（Logical Structure Design）

フェーズ: 組み立て 1/5　成果物: `07-logic/Argument.lean`（検査結果は `07-logic/report.json`）　承認: 不要

## ねらい

主張の木を Lean 4 で書き、**前提から主張が本当に導けるか**を機械的に確かめます。
さらに、あいまいな推論は公理（axiom）として明示し、それぞれに確からしさを付けます。
事実の確からしさと推論の確からしさから、主張ごとの「正しさの度合い」を帰納的に求めます。
この度合いが、本文で主張をどのくらい言い切ってよいかを決めます。

## 確からしさの計算方法

可能性論理（possibilistic logic）の考え方で計算します。

- **1つの導出の確からしさ** = その定理が依存する公理の確からしさの**最小値**。鎖の強さは、最も弱い輪で決まります。依存する公理は、Lean の `#print axioms` で機械的にたどります。
- **独立した導出が複数ある場合** は、その**最大値**。別々の根拠から同じ主張を導けるなら、`theorem claim_C0_via_cost : …` と `theorem claim_C0_via_speed : …` のように、`claim_<ID>_via_<名前>` の形で複数書きます。2つの導出が同じ事実に頼っている場合は、独立とは言えないので CLI が知らせます。
- 参考値として、依存する公理の確からしさの**積**（すべてが同時に成り立つ確率の目安）も出します。積が小さいときは、不確かな前提が積み重なっているという合図です。

## 前提のつなぎ方: 連結型と収束型

- **連結型**（すべての前提がそろって初めて言える）: `rule_C0 : P_C1 ∧ P_C2 → P_C0`。雛形はこの形です。
- **収束型**（それぞれの前提が単独でも主張を支える）: `rule_C0_a : P_C1 → P_C0` と `rule_C0_b : P_C2 → P_C0` に分け、`claim_C0_via_a`・`claim_C0_via_b` の2つの定理にします。
- 本当に全部の前提が必要か、1つずつでも言えるのかを考えて、ふさわしい形を選んでください。

## 雛形の読み方

`cyrus advance` で、`05-claims.json` と `06-facts.json` から `Argument.lean` の雛形ができています。

```lean
/-- F1: 社内アンケートで62%が検索に不満 -/
axiom P_F1 : Prop                 -- 命題（中身は docstring に書く）
/-- @fact F1 status=verified confidence=0.95 -/
axiom fact_F1 : P_F1              -- 事実。確からしさは 06-facts.json から自動で決まる
/-- @confidence TODO C1 を導く論拠: TODO -/
axiom rule_C1 : P_F1 ∧ P_F2 → P_C1   -- 推論規則。ここにあなたが確からしさと論拠を書く
theorem claim_C1 : P_C1 := rule_C1 ⟨fact_F1, fact_F2⟩
```

## 進め方

1. 各 `rule_` の docstring に、`@confidence 0〜1` と、その推論が成り立つ理由（論拠）を書く。目安は次のとおり。
   - 0.9 以上: 定義や数学的な関係からほぼ必然に言える
   - 0.7〜0.9: 一般に成り立つが、例外がありうる
   - 0.5〜0.7: もっともらしいが、別の説明も十分ありうる
   - 0.5 未満: 飛躍がある。前提を足すか、主張を弱めるべき
2. **隠れた前提を明示する。** 「AだからB」の間に暗黙の前提 X があるなら、`axiom assume_X : P_X` や `axiom rule_… : P_A ∧ P_X → P_B` の形に分解し、X にも確からしさを付ける。命題 `P_X : Prop` の宣言も忘れずに。
3. `cyrus-logic-critic` サブエージェントに `Argument.lean`・`05-claims.json`・`06-facts.json` のパスを渡し、飛躍・隠れた前提・過信を指摘してもらう。妥当な指摘は反映する。
4. `cyrus lean` を実行する。Lean が型検査を行い、各 `claim_` が依存する公理を `#print axioms` でたどって、確からしさを計算する。
   （04-analysis.md の論点のうち、主張が答えていない反論が見つかったら、ここで主張を足すか、ステージ5に戻る）
5. 結果（`07-logic/report.json`）を見て、次のように対応する。
   - 主張の中心（C0）の確からしさが 0.4 未満 → ユーザーに伝え、根拠を補強するか（ステージ6に戻る）、主張を弱めるか（ステージ5に戻る）を相談する。
   - 最も弱い根拠（weakest_link）が事実なら、追加の検証で上げられないか検討する。
   - どの主張にも使われない事実 → 本文に載せるか、ステージ8で判断する。

## 約束ごと（CLI が検査する）

- 命題は `axiom P_<ID> : Prop`。公理は `fact_` / `rule_` / `assume_` で始める。
- `rule_` と `assume_` には `@confidence` が必須。
- 主張の命題（`P_C…`）を直接公理にしてはいけない。必ず `theorem claim_<ID>`（または `claim_<ID>_via_<名前>`）として導く。
- `sorry` を残さない。
- 使えるのは Lean 4 の標準機能だけ（Mathlib は使わない）。命題論理（∧, ∨, →, ¬）で十分表せる。

## 確からしさと本文の書き方

`report.json` の各主張には hedge（言い切りの強さ）が付きます。ステージ11で本文を書くときに従います。

| 確からしさ | hedge | 書き方 |
| --- | --- | --- |
| 0.85 以上 | assert | 言い切る |
| 0.6〜0.85 | moderate | 根拠を添えて控えめに（〜と考えられます） |
| 0.4〜0.6 | tentative | 可能性として（〜の可能性があります） |
| 0.4 未満 | hypothesis | 主張にせず、仮説・未確認事項として書く |
