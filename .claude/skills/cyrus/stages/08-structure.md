# ステージ8: 文書の骨組みを決める（Document Structure Design）

フェーズ: 組み立て 2/5　成果物: `08-structure.md`（constructivism の出力）と `08-structure.json`　承認: 不要（ステージ9でまとめて承認をもらう）

## ねらい

論理の構造と文書の構造は、別の軸です。ステージ7で検証した論理（主張の木・定理・確信度・弱い前提）は文書の**核**ですが、核をそのまま並べて見せるものではありません。このステージは、核を読者の話の流れで覆う**見せ方**を決めます（`docs/workflow.md` の「大まかな構造・見せ方を設計する」）。

- 章立て（節の並びと役割）は、constructivism スキル（asuka1975/constructivism。cyrus の依存として APM で一緒に入る）に任せます。読者の目的・読む姿勢・メッセージの種別から、技術文書・学術・ビジネス文書のカタログ（チュートリアル、ハウツー、解説記事、技術記事、設計書、ADR、論文、報告書、企画書、稟議書、議事録、ポストモーテム、通知、メールなど）に照らして構成を選び、日本語の見出しの骨子を出します。
- cyrus は、その骨子の上に核を乗せます。どの節でどの主張を言うか、根拠をどこに置くか、弱い前提や範囲をどこで添えるか、論理にない材料（背景・動機・方法・用語・例）をどこに置くか。
- **主張の木を節に写さない。** 節の見出しと役割は、読者の疑問と話の流れで決まります。主張は、その中の決めた位置で言います。節1つに主張1つ、見出しは主張の文、節の最初の文も主張の文、という作り方は、論理の木をそのまま文書にしているだけで、見せ方を決めていません。

## 進め方

### 0. 手元に置くもの

| 核（ステージ5〜7） | 読者と材料（ステージ1〜4） |
| --- | --- |
| `05-claims.json`（主張の木）、`07-logic/report.json`（主張ごとの hedge、`weak_premises`、`other_theorems`）、`06-facts.json`（根拠になる事実と数字） | `03-reader.json`（purpose・questions・reading_mode）、`04-analysis.md`（読者に必要な情報・論点・載せない情報）、`01-intent.md`（種類と形式・制約） |

### 1. 読者に渡す結論の一文を作る（`message`）

主張の中心 C0 を、読者の言葉で1〜2文に言い直します。C0 は検証できる精密さで書かれているので、そのままでは読者に渡す文になりません。

- 何が分かったか、何ができて何ができなかったか、何をしてほしいかを言う。測った値は入れない（数字は根拠として本文に置く）。
- 強さは `report.json` の C0 の hedge に合わせる。
- 例: C0「語の組み合わせの相性を点数にするモデルは、生成した負例との分離では AUC 0.77 まで出た。しかし…28 組のうち 11 組を自然側とし…」→ `message`「語のペアの相性を点数にするモデルは、機械的に作った不自然さは見分けたが、人が感じる不自然さは見分けられなかった」

この一文が、constructivism に渡すメッセージになり、ステージ9の `summary` になります。`08-structure.json` の `message` に書きます（ないとエラー GT060）。

### 2. constructivism に構成を選んでもらう

Skill ツールで `constructivism` を呼びます。渡す入力は次の5項目です。すべて、これまでの成果物にあります。わかっていることはすべて渡します。
目的は必須です（渡さないとスキルは補完を求めてきます。cyrus では `03-reader.json` の `purpose` が必ずあるので、そこから渡します）。メッセージと内容は、スキルが創作して補うことはないので、必ず渡します。スキルが既定値で補うのは、専門性（中級）、読む姿勢（役職者なら冒頭だけ）、社内外と媒体（社内・Web）だけで、補ったものは出力の「仮定・逸脱」に書かれます。スキルが足りない項目を聞いてきたら、成果物から答えます（その場で作らない）。

| constructivism の入力 | 出どころ |
| --- | --- |
| 目的（読者が読後に何をするか） | `03-reader.json` の `purpose`: decide → 決める（承認）、report → 報告を受ける、act → 作業する、learn → 学ぶ、lookup → 調べる、understand → 理解する、persuade → 動かされる、verify → 検証する、summary → 要点だけ知る |
| 読者（役割・専門性・読む姿勢） | `03-reader.json` の `persona.role`、`knowledge_level`（novice → 初学者、intermediate → 中級、expert → 専門家）、`reading_context.reading_mode`（careful → 通読、skim → 拾い読み、reference → 検索、headline → 冒頭だけ） |
| メッセージ（中心の主張と種別） | 手順1の `message`（読者に渡す結論の一文。C0 の文そのものではない）と、`05-claims.json` の C0 の `message_kind`（proposal → 提言、decision → 決定の記録、report → 事実報告、instruction → 手順指示、explanation → 概念説明、comparison → 比較評価、education → 教育） |
| 内容（種別と主要な要素） | `04-analysis.md` の「読者に必要な情報」（読者の疑問ごとの項目）と「論点」から、手順的／概念的／参照的／時系列／データ中心のどれかを判断し、読者に渡す材料を箇条書きで渡す（背景と動機、何をしたか、何が起きたか、なぜか、限界、次にすること、など）。**主張の木（C1〜、F1〜）と測った値の一覧は渡さない。** 渡すと、骨子の「入れる要素」が主張の文と数字になり、節が主張の木の写しになる |
| 制約（指定書式・媒体・分量・社内外） | `01-intent.md` の「種類と形式」「制約」（社内の様式や投稿規定があれば必ず渡す。それが骨格になる）、`03-reader.json` の `reading_context.medium`（screen・mobile → Web／Wiki、print → PDF、slide → スライド、mail → メール）、`audience_scope`（internal → 社内、external → 社外。なければ社内）、分量の上限（01-intent.md に字数や枚数があればそれ。なければ `reading_context.time_budget_min` × 読む速さ（初心者 400・中級 500・専門家 600 字／分）を「約 N 字」として渡す） |

返答は「構成選択結果」「骨子」「構成チェック」の3節の Markdown です。構成チェックは、スキルの最終チェックの6項目を同じ文で `- [x]`／`- [ ]` に並べ、各項目に「判定理由」を添えた形です。**そのまま `documents/<slug>/08-structure.md` に保存します**（手を加えない。コードフェンス（```）で囲まない。cyrus check が骨子の見出しと節の対応を照合します）。
構成チェックに `[ ]`（未達）の項目があれば、保存する前に、スキルに骨子を直してもらうか、直せない理由を「仮定・逸脱」に書いてもらいます。未達のまま残すと cyrus check が警告（GT075）を出します。理由があって残すときは `--accept-warnings` で進みます。

### 3. 骨子に論理の核を乗せる（`08-structure.json`）

- `genre` ← 採用構成、`form` ← 型（PREP／SDS／SCQA／IMRaD／Diátaxis の種別など）、`style` ← 文体（敬体か常体）、`second_choice` ← 第2候補、`deviations` ← 仮定・逸脱。`title` は、ユーザーが決めた題があればそれを、なければ標題案を使う。`doc_type` には cyrus の大まかな種類（提案書・手順書・解説・報告など）を書く。`message` は手順1の一文。
- `sections`: 骨子の番号付きの項目を、順に H2 の節にする。`heading` は骨子の見出しのまま、`purpose` は「役割」、`length_hint` は「目安」、`elements` は「入れる要素」（ステージ10で、節に何を置くかの出発点になる）。必要なら H3 の小節を足してよい（骨子の見出しはすべて残す）。
- 骨子の見出しを変えたくなったら、`08-structure.md` の骨子も直し、「仮定・逸脱」に理由を書く（「選択理由」にも逸脱点を1文添える。constructivism の出力と同じ書き方にする）。
- 読者の `questions`（03-reader.json）を、それぞれどの節が答えるか割り当てる（`reader_question`）。答える節のない疑問が残らないようにする。
- **主張の置き方（`claims`）を節ごとに決める。** 置き方は3つです。
  - `assert`（言う）: その主張をこの節で述べる。**主張ごとに1節**（2節以上は警告 GT077、言う節のない主張はエラー GT068）。読者がその答えを欲しがる位置（`reader_question` に対応する節）に置く。C0 は原則として冒頭の節に置く（結論を先に。`conclusion_first` が true で冒頭の2節になければ警告 GT070）。構成の「核メッセージの位置」が末尾や両方なら、それに従う。
  - `support`（支え）: その主張の根拠・詳細・例をこの節に置く。言う節と同じでなくてよい（結論の節で言い、結果の節で支える、など）。
  - `recall`（言い直し）: まとめや次の行動の節で、言い直す。
  - 言う節の見出しに、主張の文を写さない。見出しは、読者の疑問への答えの名前か、読者が次に知りたいことの名前にする。
- **留保の置き場所（`caveats`）を決める。** `report.json` の `weak_premises`（確信度を左右する弱い前提。5つまで）の公理の名前を、どの節で条件として添えるかを書く（主張を言う節か、範囲・限界を述べる節）。置き場所のない弱い前提は警告（GT078）。`01-intent.md` の制約（検証の範囲など）や、`[不利]` の定理を限界として触れるなら、その文もここに書く。ステージ11で、ここに書いたものを日常語の条件として本文に添える。
- **論理にない材料（`material`）の置き場所を決める。** `04-analysis.md` の「読者に必要な情報」のうち、主張でも事実でもないもの（背景と動機、何をどう作ったか、用語、例、手順、次にすること）を、どの節に置くかを書く。主張の木にないものも、読者の話の流れには要る。
- **骨子に足りない役割があれば節を足す。** 核を乗せてみて置き場所のないもの（背景、なぜそうなったかの見立て、限界、次の一手）があれば、節か H3 の小節を足す（`08-structure.md` の骨子も直し、「仮定・逸脱」に理由を書く）。見立て（judgement の主張）を結果と分けて見せるかどうかも、ここで決める。
- `cyrus check` が、節ごとの見せ方を一行で見せます（GT079。例: 「S1 言う C0／留保 1／材料 1、S2 言う C1／材料 1、S3 言う C2／留保 1／材料 2、S4 言う C3／支え C1／言い直し C0／留保 4／材料 1」）。主張を言う節の割り当てしか記録されていなければ、主張の木を節に写しているとして警告します（GT077）。見出しや文が主張の写しかどうかは CLI では見ません。この一行を見て、読者の話の流れになっているかを確かめてください。

### 4. 読者の負荷の決まり（CLI が検査する）

- 最上位の節は7個まで。多ければまとめる（定型の必須セクションは削らず、第2階層を統合する）。
- 見出しの階層は3段（H2〜H4）まで。レベルを飛ばさない。
- 見出しは短く（30字以内）、見出しだけを拾い読みしても流れがわかるようにする。
- 同じ階層の見出しは形を揃える（すべて名詞止め、など）。
- スマホで読まれるなら、表を減らし、節を短くする。

## 成果物 `08-structure.json`

```json
{
  "title": "文書のタイトル",
  "doc_type": "提案書",
  "genre": "企画書・提案書",
  "form": "SCQA",
  "style": "敬体",
  "message": "読者に渡す結論の一文（C0 を読者の言葉で。測った値は入れない）",
  "second_choice": "エグゼクティブサマリー＋稟議書",
  "deviations": "補った入力はない。分量の制約で「実施計画」と「費用」を1節に統合した（逸脱条件 2）",
  "format": "markdown",
  "conclusion_first": true,
  "sections": [
    {"id": "S1", "heading": "提案の要旨", "level": 2, "purpose": "何を・いくらで・何が得られるかを先に示す", "length_hint": "10%",
     "elements": ["置き換えの依頼", "承認してほしい理由の要約"], "reader_question": "結局、何をしてほしいのか",
     "claims": {"assert": ["C0"], "support": [], "recall": []},
     "caveats": ["判断の材料は費用対効果に絞る"],
     "material": ["依頼の要約（何を・いくらで・何が得られるか）"]},
    {"id": "S2", "heading": "現状と課題", "level": 2, "purpose": "SCQA の S と C", "length_hint": "20%", "reader_question": "…",
     "claims": {"assert": ["C1"], "support": [], "recall": []},
     "caveats": [],
     "material": ["アンケートの数字"]},
    {"id": "S3", "heading": "費用と効果", "level": 2, "purpose": "費用対効果を示す", "length_hint": "25%", "reader_question": "…",
     "claims": {"assert": ["C3"], "support": ["C1"], "recall": ["C0"]},
     "caveats": ["cost_le_estimate"],
     "material": ["金額換算の仕方"]}
  ]
}
```

- `conclusion_first` を false にすると、C0 を冒頭に置かない構成も許される（チュートリアルや教材のような積み上げ型）。
- `claims` の置き方は `assert`／`support`／`recall` の3つ。`caveats` は弱い前提（`report.json` の weak_premises の公理の名前）か範囲・条件の文、`material` は論理にない材料。どちらも省略は空と同じ。

## 完了条件

- `08-structure.md` に constructivism の出力があり、骨子の見出しがすべて `sections` にある。
- 構成チェックに未達（`[ ]`）の項目が残っていない（残すなら、理由が「仮定・逸脱」にある）。
- `genre`・`form`・`style`・`message` がある。
- すべての主張に言う節が1つあり、弱い前提に留保の置き場所がある。
- `cyrus check` でエラーが0になったら `cyrus advance`。
