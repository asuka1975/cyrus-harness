# ステージ8: 文書の骨組みを決める（Document Structure Design）

フェーズ: 組み立て 2/5　成果物: `08-structure.json`　承認: 不要（ステージ9でまとめて承認をもらう）

## ねらい

文書の大まかな構造と見せ方を決めます。節（見出し）の並び、各節の役割、各節がどの主張を運ぶか、各節が読者のどの疑問に答えるかを決めます。

## 進め方

1. 文書の種類に合う型を選ぶ。迷ったら次を出発点にする。
   - 提案書: 要約（結論と依頼） → 現状と問題 → 提案 → 効果と根拠 → リスクと対策 → 依頼事項
   - 解説: 要約 → 全体像 → 部分ごとの説明 → よくある誤解 → まとめ
   - 手順書: 目的と前提 → 準備 → 手順（1節1作業） → 確認方法 → 困ったとき
   - 報告書: 要約 → 背景 → 結果 → 考察 → 次の行動
2. 読者の `questions`（03-reader.json）を、それぞれどの節が答えるか割り当てる（`reader_question`）。答える節のない疑問が残らないようにする。
3. 主張（C0〜）をすべて、どこかの節に割り当てる（`claims`）。C0 は原則として冒頭の節に置く（結論を先に）。
4. 読者の負荷を考えて、次を守る（CLI が検査する）。
   - 最上位の節は7個まで。多ければまとめる。
   - 見出しの階層は3段（H2〜H4）まで。レベルを飛ばさない。
   - 見出しは短く（30字以内）、見出しだけを拾い読みしても流れがわかるようにする。
   - 同じ階層の見出しは形を揃える（すべて名詞止め、など）。
5. 読む状況（03-reader.json の reading_context）に合わせる。
   - 拾い読みされるなら、冒頭の要約を厚くし、各節を独立して読めるようにする。
   - 引いて使われるなら、見出しを検索しやすい語にする。
   - スマホで読まれるなら、表を減らし、節を短くする。

## 成果物 `08-structure.json`

```json
{
  "title": "文書のタイトル",
  "doc_type": "提案書",
  "format": "markdown",
  "conclusion_first": true,
  "sections": [
    {"id": "S1", "heading": "要約", "level": 2, "purpose": "結論と依頼を先に伝える",
     "reader_question": "結局、何をしてほしいのか", "claims": ["C0"]},
    {"id": "S2", "heading": "いま何が困っているか", "level": 2, "purpose": "…", "reader_question": "…", "claims": ["C1"]},
    {"id": "S2.1", "heading": "…", "level": 3, "purpose": "…", "reader_question": "…", "claims": ["C2"]}
  ]
}
```

- `conclusion_first` を false にすると、C0 を冒頭に置かない構成も許される（物語的な解説など）。
